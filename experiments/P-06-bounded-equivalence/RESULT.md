# P-06 bounded-equivalence — result

Label: **Recorded (probe)**. Run 2026-10-17 on the Main-rig (AMD Ryzen 9 7950X, 32 threads, 125 GiB, Linux 7.2.5-3-omarchy, Node v26.8.1 / V8 14.x), a shared desktop with load average 18.5 (run 1) and 27.3 (run 2). Not a campaign. Precommit sha256 `7cbea8fd…e75815` and contract sha256 `c5325111…fe6674` (`receipt/*.sha256`), both hashed before either implementation was written.

## Question

Given two implementations of the same pure kernel contract — one AssemblyScript, one Rust — compiled to WebAssembly, can they be checked equivalent over a bounded input domain, and what does it cost? Does the check expose a seeded semantic fault?

## Procedure as run

- **Contract** (`CONTRACT.md`): `convert(value: i32 milli-units, fromUnit, toUnit ∈ {0..3} = kPa, psi, bar, inHg, basis ∈ {0,1}) -> i32`; exact rational scaling by `K[u]` (kPa per unit × 10^6: 1 000 000; 6 894 757; 100 000 000; 3 386 389), basis 1 adds exactly 101 325 milli-kPa before scaling; round-half-even; saturation to `[INT32_MIN+1, INT32_MAX]`; `INT32_MIN` is the error code for an invalid unit or basis code.
- **Implementations**, each written once from the contract and kept as written (no v1 copies were needed, see Results):
  - `as/convert.ts`: AssemblyScript 0.28.9 (local `node_modules`, pinned in `package.json`; `asc -O3 --noAssert --runtime stub`), i64 truncating `/` and `%` corrected to floor, `r << 1` compared with `den`. Module 316 B, sha256 `06430dfc…`.
  - `rust/src/lib.rs`: Rust 1.98.1 (`48a229cea 2026-09-01`, mise), `cdylib` for `wasm32-unknown-unknown` (target added by `rustup target add`), release with `opt-level 3`, `lto`, `codegen-units 1`, `panic = abort`, `strip`; `div_euclid`/`rem_euclid` and `(2*r).cmp(&den)`. Module 333 B, sha256 `fd0b7674…`.
- **Bounded exhaustive check** (`run.mjs`): all 32 `(fromUnit, toUnit, basis)` combinations × every `value ∈ [-2^20, 2^20)` = **67,108,864 inputs**, both modules called on each input in one loop, results compared. Each module was then timed alone over the same domain (3 passes, median). A BigInt oracle written from the contract adjudicated every disagreement (none) and was run on a stratified sample (21 edge values incl. `±2^31`, `±(2^20 ± 1)`, ties at 50/150, plus 200,000 pseudo-random `i32` values; all 32 combinations: 6,400,672 oracle comparisons per module). Invalid codes (units 4–7, 255, −1; basis 2, 3, 255, −1; `value ∈ [-4096, 4096)`): 4,653,056 inputs per module.
- **Two runs**: run 1 (`receipt/run1.json`) and run 2 (`receipt/run2.json`) are the identical procedure; the precommit said run 2 would repeat run 1 unchanged if run 1 found no disagreement, which is what happened.
- **Seeded fault** (`rust-faulty/src/lib.rs`, generated by `setup.sh` from the final Rust source; `receipt/seeded-fault.diff`): the `div_euclid`/`rem_euclid`/half-even block replaced by `let q = num / den;` (truncation toward zero). Module 237 B, sha256 `7a9c754c…`. Checked pairwise against the final Rust kernel over the full 67,108,864-input domain.
- **Extension beyond the precommit** (`extend-full-i32.mjs`, `receipt/extension-full-i32.json`, labelled as such): the two saturating combinations bar→kPa (basis 0 and 1) over the **full `i32` range**, AS vs Rust, 2 × 4,294,967,296 inputs.

## Results

### Equivalence, AS vs Rust

| Run | Inputs | Disagreements | Wall (pairwise loop) | Calls/s (both modules, pairwise) | AS alone, calls/s (3 passes) | Rust alone, calls/s (3 passes) |
|---|---|---|---|---|---|---|
| 1 | 67,108,864 | **0** | **714 ms** | 187.9 M | 163.8 M (380, 410, 413 ms) | 107.3 M (651, 626, 578 ms) |
| 2 | 67,108,864 | **0** | **692 ms** | 194.1 M | 169.0 M (397, 423, 358 ms) | 115.2 M (601, 582, 540 ms) |

- Before fix: 0 disagreements. After fix: not applicable (nothing to fix; both modules were left exactly as first written).
- Oracle sample: 6,400,672 comparisons per module, **0 wrong** for AS and **0 wrong** for Rust, in both runs. This includes the saturating inputs (`±2^31` in bar→kPa) and the exact ties (`convert(50, 0, 2, 0) = 0`, `convert(150, 0, 2, 0) = 2`, negatives likewise).
- Invalid codes: 4,653,056 inputs per module, **0 wrong** for both (every invalid code returns `INT32_MIN`).
- Extension (full `i32`, bar→kPa, basis 0 and basis 1): 0 disagreements in 4,294,967,296 inputs each; 41.9 s and 43.8 s; 205 M and 196 M calls/s pairwise.
- Whole `run.mjs` (both pairwise checks, oracle sample, invalid codes, six throughput passes): 5.8 s wall.
- **Derived** (not run): the full `i32` range for all 32 combinations is 137,438,953,472 inputs; at the measured pairwise rate that is about **0.4 h** (24–25 min) single-threaded on this machine.

The single-module throughput loop folds results into a checksum (`acc = (acc + fn(...)) | 0`) so the call cannot be elided; its per-call cost (6.1 ns AS, 9.3 ns Rust) is therefore slightly higher than the pairwise loop's (5.3 ns per call). The AS module is faster than the Rust module here by about 1.5×; the Rust module's `div_euclid`/`rem_euclid` and `clamp` compile to more branches than AS's single sign fix-up. These are V8 Liftoff/TurboFan numbers for a 20-instruction function and say nothing about the kernels' relative speed in general.

### Seeded fault (truncation instead of round-half-even), run 1 and run 2 identical

| Metric | Value |
|---|---|
| Inputs checked | 67,108,864 |
| Inputs exposing the fault | **26,177,139** (39.01 % of the domain) |
| First exposing input (enumeration order) | `convert(-1048575, from=0 kPa, to=1 psi, basis=0)`: faulty −152082, correct −152083 (oracle −152083) |
| Wall | 1,238 ms (run 1), 1,105 ms (run 2) |

Per combination: the fault is **invisible** in the 7 combinations where the rational is always an integer (kPa→kPa, psi→psi, bar→bar, inHg→inHg at basis 0; bar→kPa at basis 0 and 1; kPa→kPa at basis 1, since 101 325 000 000 / 1 000 000 is exact) and exposed on roughly half of the inputs (1,018,655 to 1,063,271 of 2,097,152) in each of the other 25 — every fractional result whose truncation differs from its nearest-even rounding. A random sample of a few thousand inputs would expose it with near certainty; a test suite that only used the exact combinations would never see it.

## What this does not show

- It does not show equivalence outside `value ∈ [-2^20, 2^20)` for 30 of the 32 combinations; the full-`i32` result exists only for the two bar→kPa combinations, and the saturation corners for the others were seen only through the oracle sample (21 edge values).
- It does not show that either module is *correct*; it shows that the two agree with each other on 67,108,864 inputs and with a BigInt oracle written by the same author from the same contract on 6.4 M sampled inputs. A misreading of the contract shared by all three would pass.
- The contract is a 4-parameter pure function over `i32` with a 24-bit value bound. A kernel with wider inputs, memory inputs (strings, arrays, state blobs) or floating point has a domain that enumeration cannot cover, and this probe says nothing about those; R19 §2.4's "small finite domains" clause is what was tested.
- Only one seeded fault, of one kind (rounding mode), was planted. The 39 % exposure rate is specific to it; an off-by-one in one saturation branch or a wrong constant for one unit would be exposed by far fewer inputs (or by none in this value range), and the precommit's own bad-sign threshold (fault exposed by under 1 % of inputs) was not exercised.
- No symbolic or SMT-level check was run (see Interpretation).
- Timings are on a loaded shared desktop (load 18–27); no CI is claimed; the calls/s figures are V8-in-Node and say nothing about Wasmtime.
- Both modules were compiled by their standard toolchains with optimisations on; the check does not cover the unoptimised builds or other toolchain versions.

## Interpretation

For a kernel of this shape the bounded equivalence check is cheap enough to be a build step: 67 M inputs in 0.7 s, 8.6 G inputs in 86 s, and the whole 32 × 2^32 space derivable at about 25 CPU-minutes. The two independently written implementations agreed on every input, including ties, negatives, saturation and invalid codes; the honest-difference disagreements the precommit anticipated did not occur, and the receipt records that rather than a staged fix. The planted rounding fault was exposed on 39 % of the domain and on the first input of the first inexact combination, so a bounded check of this size cannot miss a fault of that class. This is the "proof catches what a seeded fault is" demonstration R19 §2.4 asks for, at probe strength: it supports the claim that a refinement with a reference implementation and a small finite domain needs no seeded-fault budget, for domains that enumeration covers.

A symbolic check — translating both modules (or their difference) to SMT, e.g. with a WASM-to-SMT encoder and Z3 or Bitwuzla over 32- and 64-bit bit-vectors — would add exactly what enumeration lacks: a result over all `2^32 × 2^32` (value × code triples, including every invalid code) in seconds for a loop-free function like this one, and a counterexample when they differ. It would not add trust in the shared reading of the contract. None was run here, so the full-range statement stays Derived.
