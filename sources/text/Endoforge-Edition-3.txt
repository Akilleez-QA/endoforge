  1. The idea in one page
  Endoforge makes the creation of software an operation a running system performs, under
  rules that let the result be trusted without trusting the thing that wrote it.

  A person or an agent brings a need. The runtime finds existing capabilities, imports useful
  code, or generates what is missing; checks, runs, and measures it in a bounded workcell;
  qualifies it against an evaluator the candidate never saw; and supplies a working
  capability. Ordinary use then executes code instead of spending another model turn.

  The thesis, in the order that matters:

   1. The expensive thing is repeated understanding, not repeated compilation. Work should
      be proportional to the change and to the newly required evidence, never to the size of
      the project.
   2. Proposals are cheap now. The surrounding system exists to turn cheap proposals into
      trusted capabilities at the lowest total cost, and total cost includes the model, the
      repairs, the evaluation, the review, and the failures.
   3. A RAM-resident workcell inside one isolate is the enabler that keeps the repeated loop
      local. It is a means to the first two points, not the idea itself.

  Four commitments define the design and separate this edition from its predecessors:

        Specification is a subsystem. Every task gets an evaluator synthesized before any
        candidate exists, composed mostly from reusable invariants, qualified against fixed
        meta-gates, and confirmed in plain language by a human for its novel part.
        Trust is a measured quantity. What earns trust is the harness, never the model: the
        number of independent error sources a promotion crosses, and the measured rate at
        which seeded faults escape it.
        The candidate is a pure kernel plus declarative glue. Computation ships as a
        WebAssembly module with declared imports; views, bindings, and tests ship as data
        validated by schema. No generated imperative JavaScript executes anywhere.

        The model writes all of the code, including the trusted base, and none of it from a
        position where it grades its own work.

  The unit of success is an independently accepted useful capability per unit of total cost.
  Tokens generated, isolates created, and checks per second explain a result; they are not
  the objective.

  What should feel different: a person asks for a capability, confirms in a sentence what will
  be checked, and is using working software within a minute or two. The current version
  stays pinned while a better one is qualified. A restart restores the capability from durable
  records. A failed experiment never replaces a working version.

  This is a design document. Recorded results are marked as such; everything else is
  proposed. Section 14 is the entire evidence base. Section 15 is the shortest path from here
  to the first number that matters.

  4. The production cycle
  One request crosses five boundaries, and each boundary changes who is allowed to do
  what.




  production cycle · 5 boundaries, 1 repair loop, 1 feedback path

  Specification precedes the workcell, qualification sits outside it, and the library feeds the
  next request's evaluator rather than the next request's code.

  Intake and contract. The host establishes what is being asked, which inputs are
  authoritative, what resources may be spent, and which effects are permitted. Imported
  code is material, not authority. If the request is underdetermined, the host asks; no
  amount of synthesis supplies a missing fact.

  Specification. Before any candidate exists, an evaluator is synthesized for the task from
  reusable invariants and the request itself, qualified, frozen, and confirmed (Section 6).
  This stage is new in this edition and it precedes the workcell on purpose.

  The workcell. A RAM-resident isolate holds prepared machinery: a pinned compiler for
  each supported route, approved dependencies, a private overlay per candidate, and the
  cheap deterministic gates. Candidates are generated, checked, run against local fixtures,
  and repaired here. Machinery is reused; every candidate's mutable state is fresh.




                                                                                          Page 5 of 34
Endoforge — Software Creation as a Runtime Operation (Edition 3)




  Qualification and activation. Survivors leave the workcell as exact artifacts and meet the
  frozen evaluator, resource measurement from outside the isolate, and the promotion rule.
  Activation is a guarded revision change: the incumbent stays pinned until the
  replacement can take over without losing state, focus, or authority.

  Library and feedback. An accepted capability becomes a versioned entry with its
  contract, tests, applicability, and lineage. Its invariants and counterexamples return to the
  specification stage, which is how later requests get cheaper. Its code is the least valuable
  thing it leaves behind (Section 12).

  The model participates at three of the five boundaries: it frames the contract, it
  synthesizes the evaluator, and it generates and repairs candidates. It participates at none
  of them from a position that can promote its own output.


  5. The candidate is a pure kernel plus declarative glue
  Every candidate is a pure WebAssembly kernel plus declarative glue, and no generated
  imperative JavaScript executes anywhere in the system.

  The kernel is a WebAssembly module exporting pure functions: state in, event in, state
  out, effects out as data. Its declared imports are its only capabilities. It gets linear-
  memory isolation and no ambient authority, instantiates in well under a millisecond, and
  costs kilobytes to low megabytes per candidate (estimated) where a nested QuickJS
  guest cost tens of megabytes (recorded, Section 14).

  The glue is data: a view specification over the host's registered components, data and
  action bindings that name exact owners and revisions, interaction tests, and a result
  schema. Closed schemas validate it. The host renders it and runs the event loop. The
  candidate never touches the renderer, the broker, or the ledger.

  Three things follow. The inner candidate boundary of the earlier design, a JavaScript
  interpreter nested inside the factory isolate, becomes the module boundary itself, and the
  three-level nesting collapses to two. Pure reducers are the easiest software there is to
  test deterministically and to mutation-test, which feeds Section 6 directly. And the
  density that Edition 2 could only propose becomes arithmetic: a resident candidate is a
  module instance, not a heap.

  6. Specification is a subsystem
  For a novel request there is no fixed evaluator, so the evaluator is synthesized per task;
  what makes a synthesized evaluator trustworthy is not who wrote it but four rules it must
  satisfy and the thinness of the part that is actually new.

  Acceptance has three layers, and only the top one is synthesized.




  acceptance layers · 2 fixed, 1 synthesized, 4 rules on the synthesized one

  The lower two layers were qualified before the request arrived; the top layer is the only
  part that can be wrong in a new way, and the four rules are what keep it from grading
  itself.

   1. Universal gates, fixed for every task: contract and schema validity, type and interface
        conformance, resource bounds, determinism, forbidden effects. Deterministic code,
        run inside the isolate.
   2. Domain invariants, fixed per domain and composed per task: dimensional consistency,
      source-bound return, no cross-room mutation, round-trip and idempotence properties,
        reconciliation of totals. Authored offline and qualified once. Field OS already holds
        several. Every accepted capability adds to this layer, which is why Section 12 calls
        contracts and tests the compounding asset.




                                                                                            Page 9 of 34
Endoforge — Software Creation as a Runtime Operation (Edition 3)




   3. The task residual, the part of acceptance that only this request determines. The model
        synthesizes it from the request, the data, and any examples the person gives; it is
        stated in plain language and expressed as tests the host can run.

  The design objective is to make the residual thinner every quarter. The thinner it is, the
  less the synthesis step has to be trusted, and the more of a promotion rests on checks
  that were qualified before the request arrived.

  The residual is a candidate like any other, so it is governed by rules rather than by
  confidence:

        Before and blind. It is synthesized in a context that has seen no candidate, and it is
        shared by every candidate in the campaign. Unique per task, never per candidate, or
        nothing can be ranked.
        Frozen. Its hash enters the ledger before evaluation begins. It may be revised only on
        evidence independent of any candidate's outcome; "the test was wrong, let me fix it"
        after a failure is the most common collapse in agent loops and it is forbidden here.
        Qualified. It must reject seeded faults (swapped units, dropped rows, off-by-one,
        reversed inputs: the shape of the existing six-case fixture), accept a known-good
        anchor where one exists, and run deterministically within bounds. An evaluator that
        accepts mutants has no discriminating power and confers nothing.
        Confirmed. The person sees "here is what will be checked" before the campaign starts
        and approves it. Approving a sentence takes thirty seconds; reviewing code takes an
        hour. For the agent substrate the confirming party is the agent's own task contract.

  The rules exist because of correlated error. The failure is not a candidate editing its test; it
  is the same model reading the request the same wrong way and producing a test and a
  candidate that agree with each other. First principles make a claim calibrated and honest.
  They do not manufacture ground truth, and a synthesized evaluator is computation, which
  cannot supply a fact the request never contained. So the residual's authority is drawn
  from sources other than the generator's reading of intent wherever possible: the person's
  own examples, the data itself, differential tests against an existing implementation,
  contracts inherited from composed capabilities, and metamorphic relations that hold
  without knowing the right answer.


  7. Trust is a measured quantity
  The unit of trust is the harness, never the model, and the amount of trust a harness has is
  the measured rate at which seeded faults escape it.



                                                                                              Page 10 of 34
Endoforge — Software Creation as a Runtime Operation (Edition 3)




  In security engineering, "trusted" names a component whose failure violates the system's
  guarantees, which is why a trusted base is minimized rather than expanded. Granting
  trust to the model's run-time output does not change its error rate; it only removes
  whatever would have caught the error. Trust is therefore not something the design grants.
  It is a budget the design measures and spends.

  A harness is trustworthy to the degree its checks have independent error sources. Ten
  checks that all derive from one model turn are one check. The audit question for any
  promotion is how many independent sources it crossed.

  Three properties define the trust boundary, and none of them is human versus model:

  Two dynamics make the thresholds strict. Errors in the evaluator are silent: a wrong
  candidate fails visibly, a wrong evaluator promotes a wrong candidate with a receipt that
  says it passed. And the swarm is an optimizer: under search pressure, rare evaluator
  mistakes become the best-scoring path, so an escape rate under random sampling
  overstates safety under optimization. Section 11 returns to this.

  The compiler this project already depends on is the demonstration. tsc-rs is entirely
  model-written, and it is trusted here for three reasons that have nothing to do with trust
  being granted: it was validated against 181,711 tests ported from the Go reference compiler
  and checked on 120 open-source repositories, an oracle that did not originate in the model

  over anything, since it reads files and emits diagnostics. That is the model writing the
  code done right. The model rewriting the compiler while compiling, under trust, is what
  the boundaries above prevent.

  POODO has two roles here and one non-role. As the discipline of the proposer, it frames
  the task, separates the stated from the inferred, names the strongest rival framing, and
  decides when to stop or ask; those rival framings also seed diverse candidates, which is
  what makes parallel candidates fail independently (Section 10). As a schema, its
  precommit record (observable, acceptance boundary, oracle and oracle version, artifact
  identity, environment, failure meaning, stop condition) is the evaluation receipt of this
  design, and its separation of delivery state from outcome state is enforced in the ledger
  by deterministic code. It is not an evaluator. It runs at campaign boundaries, never per
  candidate: its own scope statement excludes routine execution, and a twenty-path
  enumeration with a mandatory research gate on every iteration would wreck the
  economics of the loop.

  The same boundaries answer the question of trust the way the project needs it answered.
  The architecture does not require that agents rarely make mistakes. It requires that
  candidates may be wrong often, that the harness catches them at a measured rate, and
  that the one component with nothing above it, the synthesized residual, is thin, blind,
  frozen, qualified, and confirmed. That is a system whose autonomy can be turned up on
  evidence as models improve, which is the forward-looking design. A system that assumes
  the trust is already there is the one that cannot tell when it has been wrong.

  Four boundary rules carry over from Edition 2 unchanged, because the evidence for them
  is the only recorded evidence this project has.

  An isolate is not a failure boundary. Isolates in one process share that process's death, its
  memory pressure, and its side channels. Partition cohorts by trust, authority, and
  acceptable shared failure; keep the controller and the ledger outside every cohort so that
  losing a process loses attempts, never the task.

  Outcome unknown is a state, not an error. An attempt authorized before a crash may
  have executed. Recovery fences future work, verifies the exact owned closure, and
  records ambiguity rather than inferring success from leftover output. A process name, a
  PID, or a successful spool is not proof of completion. Field OS recorded five named
  recovery boundaries behaving this way (Section 14).

  Limits are enforced where they work. A timeout on a blocked event loop cannot stop a
  synchronous loop. Deadlines, memory, output volume, and host-call amplification are
  enforced by the runtime, an external watchdog, or termination of an owned cohort, and




                                                                                                                    Page 15 of 34
Endoforge — Software Creation as a Runtime Operation (Edition 3)




  measurement comes from counters the candidate cannot touch.

  Waiting releases compute. A task waiting on a person, a model, or a network holds a
  continuation in durable records and no execution slot. Resumption is a fresh admission:
  source scope, context, policy, deadline, and runtime are revalidated. A swarm is a queue
  with a measured number of active slots, not a pile of idle machines.

  What changes in this edition is only the attempt row. A module instance replaces a nested
  interpreter plus its virtual filesystem, so the per-attempt footprint falls by one to two
  orders of magnitude (estimated; Experiment 4 measures it), and the inner boundary that
  Edition 2 drew around QuickJS is now drawn by the WebAssembly runtime itself.


  10. Where the time goes
  For a small novel capability the floor today is about 20 seconds and a realistic run is two to
  three minutes, and roughly four fifths of either number is model inference rather than
  anything the workcell does.




  estimated stage budgets, this edition · 3 scenarios, 7 stages

  The stages the project has engineered, the compiler, the module instance, and the local
  tests, are one to three seconds in every scenario. The person's confirmation is the only
  term with an unbounded tail, and it is a property of the request's ambiguity, not of the
  stack.

        expects about one repair round; four give a 94% chance that one passes and cut
        expected repairs to about 0.07. Sixteen buys 99.998% for four times the cost.
        Independence requires different framings, which POODO's rival-frame step produces,
        rather than different seeds on one prompt.
        Overlap evaluator synthesis with generation. Blind contexts can run concurrently; the
        evaluator's hash is frozen before evaluation, not before generation starts. This removes
        a full model turn from the critical path.
        Local inference where it pays. A permanently resident prompt cache turns the SDK
        context into warm state and cuts time-to-first-token from seconds to tens of
        milliseconds, three or four times per request. Short calls (retrieval judgments, criterion
        drafting, single-diagnostic repairs) go local; large generation stays on whichever model
        has the best yield. Decode is bandwidth-bound: on the order of 100 tokens/s for a 4-bit
        7B model on an 800 GB/s part, 30–40 for a 30B, 15–20 for a 70B (estimated), so local is



                                                                                                          Page 17 of 34
Endoforge — Software Creation as a Runtime Operation (Edition 3)




        slower per token for any model large enough to match hosted quality. Batched decode
        reads the weights once per step for all sequences, so four candidates cost close to one
        in time; that is the strongest latency argument for unified-memory hardware and it is
        Experiment 5.
        Measure the one term never measured. A model turn against the actual SDK context
        with prompt caching. Every recorded number in this project is model-free.

  The person is on the happy path only when the delivered capability needs no explanation,
  so legibility (Section 12) is part of the latency, not a separate concern.


  11. Search and improvement under a protected contract
  The factory may improve the software it makes, the process that finds it, and its own
  machinery, and it may do none of those by touching the contract that decides whether
  the improvement is real.

  A campaign freezes a task, an evaluator, a budget, and a baseline, then runs a bounded
  frontier: an incumbent plus diverse parents, a batch of proposals, cheap deterministic
  rejection first, independent measurement of survivors, and selection that keeps a Pareto
  frontier rather than one score. Many hypotheses may wait as durable records; only a
  measured number of candidates hold execution slots. A campaign stops on budget,
  plateau, regression, or ambiguous execution, and the incumbent is in service throughout.

  Three facts about optimization shape the rules.

  Optimizers find the holes in their objective. That is what optimization is. If synthesized
  evaluators are wrong one time in a hundred, search pressure does not meet that as a 1%
  nuisance; it meets the wrong evaluators as the easiest tasks and the candidates that
  exploit them as the best-scoring. An escape rate measured under random sampling
  therefore overstates safety under search, and the autonomy tiers of Section 7 are set
  against the searched rate, not the sampled one.

  Parallel samples multiply the evaluator. Sixteen candidates against a 1% leak are not
  sixteen chances to succeed; they are also sixteen chances to be credentialed wrong.
  Candidate width is bounded by the evaluator's measured discriminating power before it is
  bounded by memory.

  Repeated feedback trains on the holdout. Scores obtained repeatedly from the same
  held-out set adapt the search to that set even without access to its contents. Release
  confirmation uses rotated or fresh fixtures, paired randomized comparisons, repeated
  measurements, and real host accounting, and an inconclusive difference stays
  inconclusive.

  The arithmetic of where to spend refinement is simple and unforgiving: optimization cost
  divided by saving per subsequent use, in the same units. Two hundred CPU-seconds
  spent to save one millisecond per execution need two hundred thousand executions to
  repay the CPU alone, before model, review, and storage costs. A one-use capsule and a
  shared compiler path do not get the same budget.

  The factory's own search policy can be a challenger. It competes on fixed tasks and total
  budgets, it cannot alter the evaluator that decides whether it improved, and a change to
  that evaluator goes through Section 8's promotion path with a person at the end. This is
  controlled recursive engineering. It is not a claim of unbounded self-improvement, and the
  document does not make one.

  12. The library is inventory
  The compounding asset is the growing body of contracts, invariants, tests, and
  counterexamples; the code is the liability that comes with it.

  The factory metaphor's hardest lesson is the one Edition 2 skipped: inventory costs
  money to hold. Every retained capability carries maintenance against SDK and host churn,
  re-qualification whenever an evaluator or invariant changes, security review, and a
  retrieval cost. Retrieval itself, deciding whether a request can be satisfied by composition,
  is semantic search, which means a model call with the same latency and trust properties
  as any other. A library with no deprecation, deduplication, or reclamation mechanism is a
  landfill with provenance.

  So the library is structured around what compounds:

        A capability contract names what an operation means: schemas, required behavior,
        declared capabilities, applicability, known failure cases. It is the unit people retrieve
        and compose.
        Implementations are separate artifacts under the contract, each with its own identity,
        evidence, and resource profile. A low-startup build, a direct-WASM build, and a
        bounded fallback can coexist. A Rust rewrite is one refinement among several, and the
        measured improvement is rewarded, not the language label.
        Qualification records say which behavior was tested in which environment. They do
        not transfer: a capability efficient for one input distribution or one machine is not
        ranked universally.
        Lineage follows the data. Generated source can embed confidential values, so a
        template is split into data-free logic and scoped inputs where possible, and promotion
        never declassifies what was inlined. Every reuse is a fresh admission under current
        permissions.
        Useful failures are kept as counterexamples and constraints that narrow future
        search. A rejected candidate that revealed a wrong join rule is worth more than a tenth
        accepted parser.

  Tenant-bound lineage means most user-requested capabilities cannot be shared across
  tenants, so compounding happens per tenant unless the contracts and invariants, which
  carry no customer data, are the thing that is shared. That is another reason the contract
  layer, not the code layer, is the asset.

  A plan-phase design should also say how each part of it fares as models improve, because
  the answer is not uniform.

  Six risks are named so they can be tracked rather than discovered.

   1. tsc-rs is days old and machine-written. Its first public preview shipped on 7 October
      2026 as an experimental LLM-written Rust port of the TypeScript 7 compiler, pinned to
      one upstream revision, with documented stale-output cases under build mode and




                                                                                                                     Page 22 of 34
Endoforge — Software Creation as a Runtime Operation (Edition 3)




        memory growth in long sessions. TypeScript has no specification, so parity is a tested
        property, not a guaranteed one. Microsoft's native compiler is the parity oracle; tsc-rs
        is pinned by module hash and re-qualified on every bump; and the kernel path of
        Section 5 does not depend on it at all.
   2. The Workers memory ceiling. A type-check of a nontrivial project inside 128 MB
      alongside the harness, the overlay, and a module instance is an open question, and so is
      single-threaded WebAssembly checking speed against native. Neither number exists
        yet.
   3. Shared-process side channels. Isolates in one process are not a Spectre boundary.
      The hosted platform's mitigations (coarsened timers, dynamic process isolation) do
      not ship with bare workerd or with any self-hosted runtime. Cohorts of different trust
        get different processes, and candidate code never receives fine-grained timers.
   4. Retained capabilities as injection vectors. Data seen at generation time can shape
      code that later runs on other data, and a promoted keeper is a durable place for that to
        hide. Review, lineage that follows the data, and re-admission on every reuse are the
        mitigations; none of them scales for free, which is why review throughput is the
        binding constraint of the whole design.
   5. SDK and host churn. Every host contract change invalidates or re-qualifies a slice of
      the library, and the factory multiplies the number of dependents with no owner.
      Contracts are versioned; migrations are explicit; a capability with no passing
      qualification against the current host is retired, not quietly kept.
   6. License and provenance. The broad intake funnel admits existing scripts, libraries, and
      model output that may carry license obligations. License is a provenance field from the
      first admission, not a later audit.

  The physical-limits reasoning of Edition 2 survives as two engineering consequences and
  nothing more: movement can dominate computation (a change-aware path that touches
  256 kB instead of 1.28 GB removes a 5,000-fold term, not a 5,000-fold speedup), and when
  behavior is underdetermined by the available information no computation can supply the
  missing observation. Everything else in that discussion is background.
