01 / THESIS / PROPOSED


The concept and the bigger picture
The proposal is a general-purpose runtime that can manufacture useful software while an application is running. A
task-scoped workshop contains virtual files, a TypeScript compiler compiled from Rust to WebAssembly, a controlled
evaluator, tests, and instrumentation. An agent supplies source or a patch; the workshop checks, emits, executes, and
measures it; the host presents or activates the resulting capability. The unit of delivery becomes a small, versioned
software capsule, not necessarily a separately provisioned application.
The strongest form places the build-and-test loop inside one outer isolate. Source need not cross a remote build
service, compiler process, filesystem checkout, and deployment pipeline for every revision. The runtime retains
expensive machinery while recreating mutable task state. An isolate pool extends the same pattern to many candidates
or agents. This is a proposed synthesis; the Field OS implementation demonstrates selected components rather than
the complete loop. [R1, R2]

Why this is more than an implementation optimization
A lower marginal cost of creating software changes which problems are worth solving with software. A one-off
investigation can receive a purpose-built comparator. A user can ask for a new interaction and receive working logic
rather than an explanation of how to build it. A coding agent can try alternative implementations against a fixed
evaluator. An application can keep a useful generated module and reuse it without another model call on every
interaction.
The progression is: model output becomes executable behavior; executable behavior becomes a measured
candidate; a passing candidate becomes a reusable capability. Generative UI is one presentation of that capability.
Swarm hill climbing is one method for improving it. The runtime substrate underlies both; it is not tied to refrigeration,
Field OS, one model provider, or one UI framework.

What “everything inside” means
The compiler, virtual project, compatible tools, generated logic, local tests, and measurement hooks can inhabit the
workshop. That does not require placing model weights, operating-system services, a browser compositor, credentials,
or the authoritative evaluator in the same trust domain. Their interfaces remain explicit. A server isolate can create UI
descriptions or application modules; a browser or native host still owns display and input. [R1, U4]

 THE POTENTIALLY TRANSFORMATIVE CLAIM
 Software can become an on-demand, continuously improvable part of ordinary work—not just a product built and
 deployed before that work starts.


That is a credible architectural opportunity, not yet a demonstrated universal speedup or a claim that the underlying
primitives are new. Cloudflare already offers closely related dynamic execution and agent primitives. The differentiator
must be the complete, measured product loop: usefulness, responsiveness, correctness, resource efficiency, and safe
reuse. [U6, U7, U9, U10]

The complete workshop inside the isolate
The hot path is a local transformation from an admitted source packet to a tested module. It starts with a small, explicit
SDK and a pinned project environment. A compiler instance sees a private virtual filesystem rather than arbitrary host
paths. Compilation yields diagnostics and JavaScript; execution produces typed results, view definitions, or candidate
patches. [R1, U2, U3]




Figure 2. In-isolate target topology. Local fixture tests can run inside; authoritative scoring, permissions, and promotion remain outside
candidate control. The choice of evaluator is a host-specific implementation decision. [R1, U2, U3]

One semantic loop; two distinct compiled programs
Rust → WASM produces the TypeScript checker/emitter that the workshop loads. TypeScript → JavaScript produces
the candidate application. The candidate does not become a Rust application because its compiler is written in Rust. V8
can host the WASM compiler and compatible JavaScript; a nested QuickJS/WASM evaluator is another way to execute
generated JavaScript within the same outer isolate. [U1–U3]
The crucial reuse is the runtime and compiled WASM machinery. Fresh compiler instances still create ASTs, symbols,
type graphs, and output buffers. A warm WASM module is not automatically an incremental TypeScript program. The
inspected WASM interface creates a new instance for each run and does not support watch mode. [U2]

The runtime fabric around the workshop




Figure 3. A bounded fabric can schedule many logical tasks onto a smaller number of active workshops. Sharing engine machinery does
not imply shared mutable candidate heaps or independent process-failure boundaries. [R1, R2]

Responsibilities a senior engineer should preserve
The control plane owns task identity, current grants, queueing, admission, execution permits, resource profiles, and
state transitions. The artifact store owns immutable code, input packets, tests, build receipts, and outputs. The
execution plane runs compatible computation. The presentation host renders approved primitives or separately
sandboxed modules. None of these roles needs to become a new daemon simply because it appears as a box in the
diagram. [R1]
A trusted native adapter remains available for browser automation, native packages, full POSIX behavior, GPU work, or
a library that cannot fit the chosen WASM/Workers ABI. That is an explicit escape to a different execution class, not an
assertion that every existing npm package or application will run unchanged inside an isolate. [R1, R2]
The common interface is a capsule plus a capability contract. A browser, local workstation, site server, and managed
cloud can implement that contract differently. Avoid embedding filesystem paths, live credentials, renderer object
handles, or cloud-specific service identities into portable application logic.

Reuse the machinery, not the mission heap




Figure 4. Three lifetimes: durable task state, evictable warm machinery, and disposable attempt state. This separation enables high
logical task counts without one resident environment per task. [R1, R2, R3, U2]

An agent waiting for a model, user, or network response can persist its next step and release its execution slot. On
resume, the scheduler reconstructs a bounded attempt from immutable references and revalidates grants. A live
Promise is not a durable task record. UI state that must survive restart also belongs in the host’s versioned state model,
not only in a guest heap. [R1, R5]

Fresh-state execution does not prohibit efficient reuse. The October 8 warm trials retained host machinery while one
arm recreated the VFS per job; its median was essentially the same as the shared-VFS arm for that specific fixture. That
result supports testing this pattern, not a general proof of zero copy cost or zero cross-job leakage. [R3]
Module sharing across separate isolates or host processes is runtime-dependent. Do not assume a single physical copy
of every compiled module, declaration file, or AST across the whole machine. Cache residency, retained memory, and
eviction behavior must be measured.

Agentic coding: turn reasoning into a fast inner loop




Figure 5. Reasoning supplies or repairs a candidate; the workshop performs deterministic checking and execution. Repeated user
interactions call working code rather than regenerating the application. Proposed workflow, informed by Code Mode. [R1, U6]

A model is valuable at selecting an approach and proposing new logic. It is not necessary for every branch, loop
iteration, filter, or API-result transformation. A generated program can compose permitted tool calls, handle
intermediate data, and return compact evidence. Cloudflare documents this as Code Mode; it is a useful precedent for
keeping deterministic orchestration out of repeated model turns. [U6]

The unit of iteration becomes a patch, not an environment
For each candidate, apply a delta to the private project tree, type-check against the actual SDK, emit exact JavaScript,
run bounded tests, and return structured diagnostics. Retain dependency machinery and the compiled checker. Do not
reinstall packages or respawn a full build toolchain simply because a generated function changes. This is the target
architecture, not the current Field OS gateway, which still accepts a prebuilt self-contained script. [R6, R7]
The agent can then use the compiler as rapid feedback: missing method, wrong parameter, incompatible state shape,
or invalid result contract. Type checking prunes structurally invalid candidates before expensive behavioral or UI tests.
Semantic correctness still requires independent tests and source validation; a type-correct hallucinated formula
remains wrong.

Reason once, execute many times
A useful comparator, parser, mapper, or interaction handler can be reused after generation. The cost of reasoning and
checking is amortized across subsequent executions. New reasoning is needed for new intent or unresolved behavior—
not necessarily for every click. This may reduce model round trips and intermediate context, but a large search over
candidate programs can also consume more tokens. Count total search cost, including failed candidates, rather than
assuming a swarm is cheaper.

Generative UI becomes working software




Figure 6. Generate a candidate UI version without mutating the active one. Validation and state-compatible activation turn generated
output into a working instrument. Proposed general lifecycle; Field OS supplies source-binding requirements. [R1, R9]

The UI is no longer only a generated screen. A capsule can contain typed view structure, calculation logic, input
validation, state transitions, sorting and filtering, and explicitly bound actions. The existing application supplies
rendering, styling, accessibility, data access, and effect approval. Working code handles interaction after the initial
generation.
For example, a user investigating inconsistent measurements could receive a comparison panel with unit controls,
source links, uncertainty labels, and a discrepancy table. A later request could add a sensitivity plot or change the
grouping. The host compiles and tests version N+1 while N remains usable, then activates the new version without
losing the user’s selection or source context. This is a proposed interaction, not a recorded Field OS UI result.

The stable contract is more important than the visual novelty
Use a versioned presentation grammar for common controls and views; use a separate, capability-limited application
sandbox when the grammar is insufficient. Preserve identity, input focus, unsaved state, keyboard behavior, accessible
names, and rollback. An updated layout must not silently reinterpret a number or redirect an action to a different
object. Field OS’s exact room/source bindings illustrate why UI state and domain authority must remain distinct. [R9]
UI improvement needs a real renderer test. Structural schema validity cannot establish legibility, navigation,
responsiveness, or task completion. A candidate may be better because it exposes fewer misleading options—not
because it renders more components. Keep high-consequence action approval in the host, outside generated
presentation code.

Swarm hill climbing: generation with measurement




Figure 7. A bounded search population generates candidates inside isolated workshops. An independent harness measures exact
artifacts; selection preserves an incumbent and a budget. This complete swarm loop is proposed, not yet measured in the Field OS
receipts.

A swarm does not need a separate operating environment per agent. It needs independent candidate state, traceable
lineage, and enough execution slots for the available CPU, memory, and inference budget. The runtime can keep many
candidate records while only a few workers are active. WASM checking can reject malformed variants before more
expensive evaluation.
Each generation starts from an incumbent and selected diverse parents. Workers propose different algorithms, data
structures, view layouts, or task strategies. The harness first enforces hard correctness and policy gates, then measures
objective quality, latency, CPU, memory, and user-task outcomes. A challenger replaces the incumbent only when it
clears the declared acceptance rule.
Plain hill climbing can plateau or overfit its evaluator. Preserve diversity, use restarts or alternate objectives when
justified, and keep untouched holdout tasks. More candidates increase the chance of finding both a useful
improvement and a lucky measurement. Repeated trials and held-out evaluation are therefore part of the architecture
—not optional reporting polish.

Build a trustworthy optimization loop
Separate hard constraints from optimization objectives
A performance improvement cannot compensate for wrong answers, broken accessibility, data leakage, or
unauthorized effects. Evaluate validity first. Among eligible candidates, compare a vector of outcomes rather than
hiding all tradeoffs inside one score. A faster implementation that doubles memory may be suitable on a workstation
and unsuitable on a small appliance.

 Stage                 Required evidence                                                           Who controls it

 Contract gate         Source/build identity, schema compatibility, capability ceiling             Trusted controller

 Behavior gate         Independent assertions, invariants, regression fixtures                     Evaluator outside candidate scope

 Resource gate         Deadline, peak memory, CPU, output volume, cancellation                     Host / kernel / managed runtime

 UI gate               Task completion, interaction parity, accessibility, state retention         Renderer harness and human review

 Selection             Repeated comparisons; held-out confirmation; declared tradeoff              Frozen acceptance policy

 Promotion             Exact artifact, proof bundle, current grants, rollback identity             Authority owner



An implementable search skeleton
incumbent = load_verified_baseline(task_revision)
while budget.remaining() and not stop_rule.reached():
     parents = select_diverse_parents(incumbent, archive)
     proposals = generate_bounded_variants(parents, public_feedback)
     for candidate in scheduler.admit(proposals):
             build = workshop.check_and_emit(candidate)
             if not build.contracts_pass: record_rejection(build); continue
             evidence = trusted_harness.evaluate(build.exact_artifact)
             archive.append(candidate, build, evidence)
     challenger = select_eligible_candidate(archive, frozen_objective)
     if heldout_accepts(challenger, incumbent):
             incumbent = commit_candidate(challenger, expected_revision)
return incumbent, complete_search_receipt
This is proposed orchestration pseudocode, not an existing API. The candidate must not alter the evaluator, scoring
weights, hidden fixtures, timing boundaries, or its own host counters. Generated tests may supplement—but cannot
replace—the independent acceptance oracle.

Guard against measurement-driven failure
Record seeds, code and input digests, runtime versions, CPU quota, warm/cold state, contention, and compiler mode.
Randomize trial order and use paired comparisons where possible. Keep validation feedback useful but prevent
repeated exposure from turning the holdout into training data. For noisy UI and task-quality objectives, require human
evidence where automation cannot establish usefulness.
Stop on budget exhaustion, plateau, regression, or ambiguous execution. Keep the incumbent working throughout. A
failed candidate is evidence, not permission to weaken the objective after seeing its result. Count all model, compiler,
test, rendering, storage, and reviewer costs in the final search receipt.

Where speed and resource advantages come from
There are three distinct levers: amortize setup, shorten deterministic feedback, and remove unnecessary reasoning
turns. Shared machinery does not make CPU work free, and a compiler speedup is not automatically an application
speedup.
T_cycle = T_model + T_queue + T_prepare + T_check
          + T_test + T_measure + T_publish


M_substrate ~= M_host + M_warm_pools
                   + sum(M_private_files + M_compiler_instance
                         + M_guest + M_buffers) for active attempts
                   + M_bounded_caches
The memory expression is an accounting model, not a measured allocation. Sequential phases may release compiler
state before the guest reaches peak memory, so observed peak can be smaller than the sum; overlapping work and
handoff copies can increase it. Containers already share a kernel and may share image/cache pages. Compare
incremental resident memory and proportional set size where available, not a fictional full OS copy per container.

Do not multiply unrelated benchmark ratios
If checking occupies fraction f of a fixed workflow and becomes s times faster, the idealized total speedup is 1 / ((1 − f)
+ f / s). At f = 0.60 and s = 10, that is about 2.17×; at f = 0.10, about 1.10×. Removing whole model or deployment steps
can change the workflow itself and create additional gains, but those must be measured separately.
For swarm search, active throughput is bounded by CPU-seconds, memory headroom, compiler concurrency, model
limits, and evaluator capacity. A single-threaded isolate does not turn many CPU-bound candidates into parallel CPU
execution. Schedule them across suitable workers/processes or machines; do not make the UI event loop carry an
unbounded compiler queue.

 THE RIGHT UNIT OF SUCCESS
 Measure time and total resources per accepted useful capability—not only checks per second, isolates created, or
 the fastest successful candidate.

WASM turns the compiler into a runtime component
The inspected WASM package describes a 4.2 MB compiler module, about 1.8 MB gzip or 1.5 MB Brotli, including
compressed TypeScript libraries. A larger 5.2 MB build is reported to check 13–18% faster. The package documentation
says publication is not enabled: this is a source-buildable interface, not a verified published WASM dependency to
install blindly. [U2]

What the embedding surface actually supplies
Its runtime-independent core accepts a compiled WebAssembly module and a host filesystem interface. The high-level
in-memory interface maps absolute virtual paths to file text and returns diagnostics and emitted files. The core supplies
a small WASI shim and filesystem bridge; it does not require Node’s WASI filesystem. This makes an in-isolate adapter
plausible, but the inspected documentation does not establish a completed workerd integration. [U2, U3]

 In-memory files and structured
                                      A generated patch can be checked without a host project checkout.
 diagnostics

 No watch, LSP, or API mode in this
                                      Do not describe a persistent incremental language service as already implemented.
 WASM interface

 Host-dependent stack behavior        Stress deep types and syntax on the actual runtime before admitting arbitrary projects.

Binary size is not runtime memory
A 4.2 MB download does not imply a 4.2 MB isolate, heap, or project check. Include compiled machine code, WASM
linear memory, AST/type graphs, source strings, duplicate encodings, emitted modules, VFS data, stacks, and host
buffers. The Node wrapper’s documented 256 MB worker stack setting is not evidence that every host commits that
much memory; it is also not an available Workers setting by default. [U2]

The minimum embedding work
Bundle a pinned compiler module, supply an allowlisted virtual filesystem and SDK, adapt clocks/random/output
imports as required, enforce source and depth limits, compare diagnostics and emitted bytes to a pinned reference,
then connect a host-supported evaluator. Module resolution and bundling are separate obligations: tsc emission is not
proof that runtime imports resolve. Lock dependencies; never let a generated candidate install arbitrary packages
during execution.
Once this works, the application can treat compilation as an ordinary runtime capability. That is the enabling step for
the proposed “everything inside the isolate” loop—not a claim that the whole operating system or inference engine fits
inside it.

Cloudflare: exact execution topology matters




Figure 9. Two valid implementation shapes. A keeps build and execution in the same outer isolate. B uses a compiler Worker plus a
separate execution isolate. B stays inside the Workers platform but is not literally one isolate. [U2, U3, U7, U8]

Strict in-isolate form: run the WASM checker, virtual files, and tests in the workshop. Generated JavaScript then uses
an explicitly permitted host evaluation API or a nested JS/WASM interpreter such as QuickJS. The nested route
maintains one outer isolate but introduces another engine and its overhead. Executing directly in a privileged realm is
not an isolation boundary; type checking does not make it safe.
Managed Worker Loader form: a compiler Worker produces a module map and a loader creates an execution Worker.
Current documentation distinguishes load() for a fresh Worker from get(id, callback) for potentially warm reuse.
Content and configuration changes require a new identity, and cache residency is not guaranteed. [U7]
Cloudflare’s Dynamic Workers playground already documents runtime TypeScript bundling, dynamic execution, and
bundle reuse. That establishes relevant adjacent functionality, not full tsc-rs semantic type checking or the complete
measured search loop proposed here. The loader consumes executable modules; checking and dependency
preparation must happen before that handoff. [U10]

What must be verified on the chosen host
Do not rely on arbitrary request-time eval, assume Node worker-thread support, or feed raw WASM bytes into an
unsupported compilation path. Cloudflare documents instantiation of precompiled WASM modules; the loader has its
own module-loading surface. A successful import is not proof that the compiler adapter, stack behavior, or evaluator
works in that environment. [U7, U8]
For generated code, explicitly block ambient egress and pass only narrowly scoped bindings. The current loader
defaults to inherited outbound access when no override is specified; globalOutbound: null cuts off its global
network access. Binding calls remain capabilities and must be governed separately. [U7]

Cloud implications, prior art, and differentiation
What this implies for Cloudflare and similar platforms
An isolate platform can become a host for software-producing workloads, not only predeployed handlers. Small
generated modules can sit near their tools and data, reuse platform machinery, and become callable capabilities. The
compiler can itself be a WASM component of that environment. The opportunity is a common build/check/run/observe
contract across local applications and managed execution—not an obligation to deploy a separate server per generated
instrument.
Cloudflare’s workerd README describes compatible nanoservices sharing a thread and process and connected through
capability bindings. Cloudflare Code Mode documents generated programs that compose tools. Project Think describes
durable execution, child agents, sessions, dynamic execution, and self-authored extensions. These are substantial
precedents: the opportunity cannot be presented as “nobody has considered agents writing tools inside a runtime.”
[U4, U6, U9]

Hosted Workers and self-hosted workerd are not the same guarantee
At the inspected workerd revision 587bab1, the factory source still contains null isolate and request limit enforcers
under its single-tenant policy. The README also warns that workerd alone lacks the defense-in-depth required for
potentially malicious code. Therefore a self-hosted design must provide appropriate outer containment, watchdogs,
and resource accounting rather than inherit hosted security or quotas by implication. [U4, U5]
If a worker process must be killed to stop runaway code, every in-flight member of that process can fail. Cohort size is a
performance and fault-isolation decision. Partition by trust, authority, memory budget, and acceptable shared failure—
not just maximum density. Persist attempts outside the group so process loss does not erase the task history. [R1, U5]

 Opportunity                         Required differentiation

 Point-of-need applications          A useful interactive result, not merely successful generated code execution.

 Dense agent execution               Measured incremental memory and idle occupancy under realistic concurrency.

 Embedded semantic checking          Pinned compiler parity and in-isolate latency, not transpilation alone.

 Measured generative UI              Behavior, task completion, accessibility, and continuity—not screenshots alone.

 Swarm improvement                   Better accepted results at an equal complete budget, with frozen evaluation.


Potentially transformative outcomes do not require inventing every primitive. They require an integration that changes
the cost, latency, or usability threshold enough to enable a new class of everyday software. The proposed workshop
should be judged on that evidence, not on a platform-replacement narrative.

source-bound field instruments in a native Linux environment. Existing Python owners retain identity, permissions,
ledger state, evidence custody, and candidate projection. [R1, R6]
The private gateway accepts a self-contained JavaScript script staged from admitted content-addressed objects. It
verifies the runtime closure and current source authority. Its small adapter creates fresh QuickJS and VFS state,
removes underlying tool/fetch/command ports, and returns bounded candidate JSON. The installed application is not
switched to this private path. [R6, R7]

Why this case study matters beyond the domain
It supplies concrete observations about warm machinery, fresh mutable state, bounded execution, provenance, and
crash recovery. Those lessons transfer to a general software substrate. It does not establish a shared V8 workerd
deployment, in-isolate tsc-rs speed, generative UI usefulness, swarm convergence, or appliance-wide energy savings.
[R3–R5]
The output remains a candidate. A guest cannot establish approval by returning accepted: true; the host’s envelope
retains generated, unreviewed, and unapproved status. Source access and integrity are rechecked on later projection.
That distinction is equally relevant to generated business tools, coding assistants, and analytical UIs. [R5]

20 / RUNTIME OPERATIONS / PROPOSED


Operating the substrate across hosts




Figure 13. The portable unit is a capsule and checkpoint contract—not an assumed migratable live heap. Host adapters determine
storage, UI, networking, native tools, and enforcement.

Scheduling and backpressure
Start with explicit limits on runnable queue size, active compiler instances, guest concurrency, and total memory.
Separate UI interaction from background candidate search. Throttle speculative swarms before capture, user input, or
durable-state work is affected. Parallelism should follow measured bottlenecks; aggressive native checker threads can
reduce the number of candidates that fit. [R1, U1]

Cancellation and containment
Use an external deadline mechanism capable of terminating the actual execution unit. A timeout scheduled on the
same blocked event loop cannot stop a synchronous CPU loop. Bound compiler input, filesystem size, decompression,
output, host bridge traffic, and broker amplification. Keep secrets and canonical state outside candidate namespaces;
read-only mounting of a sensitive host file still exposes its contents. [R1, R7, R8]

Publication and lifecycle
Store immutable outputs before committing references. Activate by a guarded revision change; do not replace active
code during partial compilation. On failure, keep the incumbent and a bounded diagnostic. Reconstruct waiting work
from durable references after eviction or restart. Treat caches as optional acceleration, not a correctness dependency.
[R1, R5, U7]
Collect per-phase latency, CPU, peak and retained memory, model usage, bytes copied, cache hit/miss, checker mode,
active queue pressure, failure cause, and artifact/evaluator identities. After teardown, verify that the intended
resources were actually released. Count renderer and broker work outside the guest group when reporting whole-
system efficiency.

 A user requests a working interface; bounded workers generate alternatives; the WASM compiler and tests reject

Stop or narrow the approach if diagnostic parity fails, host memory erases the density benefit, evaluator cost

experiment can change the implementation without invalidating the broader product goal.

22 / SYNTHESIS / CONDITIONAL IMPLICATIONS


What changes if the complete loop works
Applications become compositions of generated capabilities
Instead of selecting a prebuilt application that approximately matches a task, a user could receive a tailored working
surface inside an existing environment. Stable domain objects, capability contracts, and renderer primitives provide
continuity; generated code supplies the task-specific behavior. Field OS is one setting. The same mechanism could
support analytical workbenches, coding tools, support operations, internal workflows, education, simulation interfaces,
or personal computing.

The environment becomes a software workshop
The compiler is no longer only a developer workstation utility. As a portable WASM component, it can participate in an
application’s runtime. The runtime becomes a place where software is proposed, checked, rehearsed, compared, and
retained. Dependency preparation and host interfaces still matter, but they become shared infrastructure rather than
repeated setup for each small tool. [U2, U3]

Improvement becomes an accountable loop
Generative UI and swarm search reinforce each other: software candidates can vary both behavior and interaction,
while fixed evaluators measure whether the changes actually help. Faster checking and lower execution overhead
permit more experiments within a budget. That does not guarantee convergence or correctness; it makes a disciplined
search process more affordable.

The model is used where it adds value
Reasoning chooses and revises a strategy. Compiled or interpreted code performs repeatable operations. A successful
program becomes an asset that can run without repeating the original reasoning. This moves some work from recurring
inference into reusable software. It is an economic hypothesis to test at the whole-task level, not an assertion that
model cost vanishes.

The claim that can be made today
The local receipts establish warm guest reuse, fresh-state execution, guarded admission, candidate custody, and named
recovery behavior. Upstream reports establish a fast native Rust TypeScript checker and a source-buildable compact
WASM interface. Cloudflare supplies relevant dynamic execution and agent primitives. Together they support a serious
engineering path to the proposed substrate. They do not yet establish its end-to-end speed, resource advantage, UI
usefulness, or swarm-search benefit. [R3–R5, U1–U10]

 BOTTOM LINE
 The opportunity is not merely “a faster coding agent.” It is to make the creation and measured improvement of
 working software a routine capability of the application runtime itself. That could be a category-level change if the
 complete loop clears its technical and user-value tests.


Implementation priority: prove a small, fully in-isolate compiler/evaluator loop first; attach one useful generative
interface; add independent measurement and bounded variant search; then scale only the dimensions whose complete
economics have been demonstrated.
