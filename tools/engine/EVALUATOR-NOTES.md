# EF-06 / WP09b evaluator engine

The owner's EF-06 packet authorizes this implementation in the supplied stack. Git mutation and publication remain with the orchestrator. The jobs-board connection is audit-ready evidence and checking readings. The governing criteria are WP09 in `docs/execution/WORK-PACKAGES.md` (this checkout has no separate WP09b) and Edition 3 sections 6, 8 and 11: three acceptance layers, frozen identity, explicit unknown outcomes and Pareto selection. The happy path is a frozen evaluator, passing candidates, independent measurement and fresh finalist checks.

The parts search found the existing universal gates and factory-quality validators, and EF-02's frozen store. The wall's Pareto item is an LLM analysis tool, not a numeric dominance implementation. This engine reuses `runUniversalGates` and calls Python's `FrozenEvaluators.require_frozen` through a bounded subprocess. It does not duplicate the store's digest or canonical encoding. No existing expected results or fixtures changed.

`evaluateCandidates(reference, candidates, port)` takes `{ledger, root, identity}` with absolute paths to an existing ledger and evaluator tree, plus distinct candidate identity strings. The stored bundle's configuration supplies `gateInput` (the universal-gate envelope without candidate), `invariants` (an explicit ordered list, possibly empty), and `objectives` (metric names mapped to `min` or `max`). Freeze this configuration with the existing EF-02 command; weights are invalid. Configuration, residual text, invariant version and code bytes all come from that frozen record. An invalid initial reference or engine configuration refuses the call before any candidate operation.

The host port retains `describe`, `run` and `scanEffects` from EF-05. It adds `invariant(name, candidate, bundle, round)`, `residual(candidate, bundle, round)` and `measure(candidate, bundle, round)`. Invariant and residual methods return `{passed: boolean, reason: nonempty string}`; measure returns exactly the declared metric names with finite numeric values. All methods may be async. Each receives its own snapshot of inputs. The bundle includes frozen file bytes, configuration, residual and invariant version; trusted adapters must consume these frozen inputs, pin candidate bytes, enforce execution bounds and provide independent measurements. This engine is not an isolate or a defense against a dishonest host adapter.

Order is frozen verification, the five universal gates, each named invariant, residual, measurement, then frozen verification again. Any failed check stops that attempt; its record names one firstFailure and includes only executed checks. Only successful attempts enter Pareto comparison. A dominates B only when A is no worse on every objective and strictly better on at least one. Ties and incomparable tradeoffs survive. There is no weighted sum or tie-breaking score.

Round 0 evaluates every candidate sequentially. Its Pareto frontier enters round 1, which repeats all acceptance layers and obtains new measurements; universal gates require two fresh isolated runs within each round. The returned frontier uses round-1 measurements only. A failed finalist is removed; previously dominated candidates are not automatically retried. Empty frontier is valid. The deterministic report records each attempt's candidate, round, frozen identity and digest, results, metrics, stage and firstFailure; the report also identifies the shared evaluator.

Thrown host operations or explicit `{status: 'outcome_unknown'}` stop the campaign with that stage and an empty frontier, including during finalist checks. Malformed completed evidence is rejected. Drift between candidates or during measurement stops selection. Initial frozen verification errors reject the API call; drift detected during attempts becomes an attributed frozen failure. Exceptions do not establish candidate incorrectness.

Scope: this is a selection engine, not promotion. Remaining integration slices are durable attempt/observation journalling and crash reconciliation, production sandbox and domain/residual adapters, and a campaign controller with budgets and retry policy. The frozen identity already exists durably before any evaluation; returned attempts are not yet ledger receipts. Actual candidate linkage to ledger records belongs to that receipt integration. Host process crashes cannot be recovered from these in-memory reports alone.

Measurements and learning: baseline engine tests passed 10/10. The first implementation passed 17/17 and the full suite. Review identified that explicit unknown host statuses needed the same stop behavior as exceptions; added the shared invocation guard and controls for unknown runtime/finalist results and fresh measurement ranking. Cost: one local revision and a full-suite rerun. No tests failed during implementation. The runner is sequential and the store subprocess has a 10-second timeout and 16 MiB response limit; actual candidate execution limits remain enforced by the EF-05 host-port contract.

Final review also closed the configuration envelope so unexpected policy fields cannot be silently ignored; added controls for weights, duplicate invariants, candidate-specific policy and duplicate candidate identities. Final full suite: 19 engine, 18 ledger/freeze, 16 lifecycle and 8 X1 tests passed; documentation had 0 failures and 12 existing warnings; all 19 pinned Mononoke sources verified. Node syntax, Python in-memory compilation/tokenization, comment absence, whitespace and Git diff checks passed. The requested PR handoff is `/tmp/ef-06-evaluator-engine-body.md`.
