# EF-01 / WP04a

The assigned deliverable is five Ledger v0 records: task, admitted input, frozen evaluator, candidate and receipt, with JSON schema and an append-only writer. The checked-out work-package document and GitHub main define WP04, but contain no WP04a. This packet implements the requested subset; build coalescing, activation CAS, overlay reclamation and evaluation-process recovery remain outside it.

Demand: the owner's EF-01 packet, supporting the jobs board's audit-ready evidence and job handoff. Happy path: append task, admitted input, frozen evaluator, candidate, then receipt; reopen and verify the same records. R11 governs publication after closure and independent delivery/outcome states.

Reuse: the parts wall's `hash-chained-event-ledger` SQLite pattern and `oss-rekor-name-the-canonicalization` principle; the existing factory state journal supplies the fail-closed replay pattern. No wall files are changed because this packet owns only Endoforge.

The public API is `Ledger(path).append(record)` and `Ledger(path).records()` in `tools.ledger.ledger`. Records conform to the adjacent Draft 2020-12 JSON schema. The internal schema interpreter implements only the keywords used by that fixed schema. All payloads are inline text; references identify earlier committed records of the required kind and task. A receipt also binds the candidate and evaluator to the same admitted input. Freeze ordering is the commit sequence, not a caller's clock. A new evaluation uses a new receipt ID; duplicate IDs are refused even when bytes match.

SQLite FULL synchronous commits and an immediate transaction serialize writers. SQL triggers also refuse update, delete and replacement. Each event hashes its sequence, previous hash and exact stored ASCII JSON bytes. Serialization uses Python sorted keys, compact separators, ASCII escapes and finite JSON values; this is not RFC 8785. Reopen and every append verify the full chain. This is a trusted local writer API, not a security boundary against a database owner who can remove triggers or rewrite the whole database; suffix loss requires an external checkpoint to detect. Payload text is stored, never fetched or executed. The writer cannot prove that an external evaluator ran its claimed content or that an observation is true.

The worktree's shared Git metadata is read-only; sync failed before any change. Python has no jsonschema package, so the writer stays stdlib-only. The missing WP04a criteria and Git publication restriction are tracked gaps.

Review added refusal of temporary databases, nonfinite JSON and mismatched precommit oracle identities; `make -C forge/endoforge test` then passed all 35 tests (8 X1, 16 lifecycle, 11 ledger), the documentation check (zero failures, 12 unchanged warnings), and all 19 pinned-source verifications. # EF-03 / WP05

Demand and authorization: the owner's EF-03 worker packet extends EF-01 in this worktree; git is read-only and publication belongs to the orchestrator. The audit-ready evidence and handoff jobs apply. WP05 in `docs/execution/WORK-PACKAGES.md` governs the fields and acceptance. No new fan-out, model spend or production run is involved.

Current writers use `Ledger.admit(record)` with schema version 1. Every v1 record requires provenance (origin, upstream identity/version, visible input scopes, durable derivation parents) and license (expression and evidence SHA-256). Generated records also require model identity/version. Shape checks cannot establish SPDX membership, evidence-file contents or truthful declarations. The schema interpreter remains stdlib-only.

Compatibility is explicit: `append(record)` retains the EF-01 v0 interface and also validates v1 records. Legacy v0 records have neither metadata field; partial or v1 metadata cannot masquerade as v0. `records()` returns original records, and replay leaves their bytes and hashes unchanged. `lineage(id)` adds `provenance_status: provenance-unknown` to legacy query results only. It does not invent license facts, rewrite history or claim that unknown ancestral scopes are empty. New callers must use `admit`; legacy callers of `append` must deliberately migrate to it.

Pin `data.precommit.no_unknown_licenses` on the immutable task before admitting material. When true, imported and pre-built WASM records with an unknown license are refused. Missing policy allows explicitly unknown licenses. Lineage follows typed data references and explicit derivation parents in admission order. Parents must already be durable and belong to the same task; each child retains all declared parent scopes. A v0 record cannot reference a v1 source, including a v1 task, so legacy append cannot erase metadata or evade a current task's policy. A v1 child may extend a legacy task and its lineage still exposes the unknown ancestors.

WP05 integration gaps: EF-01 has no separate artifact, resolved-source or activation/promotion API. Linked successors test preservation through `derived_from`, not an implemented activation lifecycle. A caller that omits a derivation cannot be detected from inline content alone.

Learning: requiring new fields on v0 broke ten protected EF-01 tests and old-database replay. The first attempt's cost was one rejected handoff and 10 failing tests (3 failures, 7 errors). Versioned validation and a separate current admission API close the compatibility defect without changing protected fixtures. Regression coverage checks legacy records/hashes, unknown reporting, mixed lineage, downgrade refusal and v1 replay with missing metadata despite a valid hash. The earlier test-helper `origin` collision was fixed before execution at the cost of one small patch.

Continuation checks: `make -C forge/endoforge ledger-test` passed all 25 tests, including all 11 unchanged EF-01 tests. `make -C forge/endoforge test` passed: 49 tests (8 X1, 16 lifecycle, 25 ledger), documentation zero failures/12 existing warnings, and all 19 pinned sources verified. JSON parsing, whitespace, unchanged-fixture and zero-comment checks passed; all five changed/new repository files stay under Endoforge (348 changed lines including the new test file). The PR handoff with every check is `/tmp/ef-03-provenance-body.md`, as explicitly requested. No git metadata was written.
