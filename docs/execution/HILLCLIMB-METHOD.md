## Purpose

Edition 3, the factory protocol, the gates, the claim ladder and this method are the **incumbent**: the best current hypothesis about how to make useful capability cheaply, to be beaten, not obeyed (owner, 17 Oct late evening: deviate from the initial spec with better ideas; a spec treated as law never improves). Make the reasoning that followed the first run repeatable: measure where time, cost and rejections go; name the binding constraint; move the whole stack against it; decide adoption on a signal the optimised agents cannot read or game; make cross-stage interactions ("meta-opportunities") visible as tested hypotheses rather than impressions; touch the true objective (a person using a capability) every loop; record forecasts and score them. The constraint migrates (today: setup → model term → intent); the loop exists to notice when it does.

## The objective the loop climbs

**Pass rate on frozen persona-written evals, on fresh real requests (v2.4, DEC-79).** For every request, persona agents (technician, engineering reviewer, safety, and the requester's own frame; more than one model family) write **executable evals** from the raw request **in parallel with the generator and blind to its code**: worked cases with tolerances, the facts that must be asked rather than assumed, refusal rules that must name the input at fault, ranges and physical bounds, units and precision, required sources. The evals are frozen and hashed before any kernel exists; deterministic gates run them. A request is *clean* when the factory promotes it **and** the artefact passes every frozen persona eval. Agents write evals; no agent scores an artefact after the fact.

*Superseded definition (v2.0-v2.3, loop 1):* clean = promoted and confirmed by a sealed consumer-oracle panel scoring the artefact after it was built. Loop 1 showed why this drifted from the design: the panel did mechanical checks by judgement, cost more than generation (L-26), and disagreed on reference truth.

**Guardrails (adoption blocks if any worsens beyond its pre-registered bound):** gate pass rate on independent re-run; median wall per request; tokens per request; determinism and bounded time; canary recall (below); seeded-fault escape rate once measured per request. **Efficiency** (cost per clean promotion, with tokens priced at list price, wall in seconds and owner minutes priced, weights pre-registered per loop) is the secondary that ranks winners among non-inferior challengers; it never decides adoption on its own.

## Eval design (DEC-80, v2.5)

- Eval writers see the request and the bare signature only (names, arguments, units); never the stub's assumption, defaults, formulas or question. Two writers, two model families.
- Interface evals: every decision-relevant fact needs an input path; a fact is decision-relevant only when two plausible values give expected outputs that differ beyond tolerance.
- Physical validity: general checks (finite inputs, declared ranges, sign and unit sanity) are a deterministic library in Endoforge; domain bounds (for refrigeration: critical points, saturation limits) come from the consuming project's reference provider (DEC-81).
- Value references come from that provider, declared per run (name, version, source, hash), never the same table the kernel uses.
- A failing frozen eval is invalidated only by outcome-independent evidence; the repair agent never edits evals.
- Requests outside the artifact class form their own reported stratum.

## Eval quality without judges (DEC-79)

The evals are the ruler, so their own quality is measured by machine means, never by an agent grading artefacts:

- **Independent eval writers.** Two persona agents on different model families write evals for the same request; a case where their expected values or refusal rules disagree is flagged and resolved by computation against the shared property core, or dropped before freezing.
- **Deterministic consistency checks before freezing.** A validator checks every eval against the typed contract: non-finite values encoded, no case expecting a value inside a declared refused range (the R-02 failure), units and tolerances declared (S-10, D-11).
- **Canary capabilities.** Known-defective artefacts (wrong default, wrong question, unenforced range) must fail the evals: canary recall 3/3 or the evals are void.
- **Mutation testing.** Planted faults in a known-good kernel must be killed by the evals; the kill rate is reported per eval suite.

## The sealed oracle panel and the canaries (no human step)

- **Sealed consumer-oracle panel:** two isolated agents that no production or optimiser agent ever reads or is read by, on **different models from the generators and from each other** (today: generators on the session model, oracle A on Sonnet 5.5 in a field-technician frame, oracle B on Opus 5.5 in an engineering-reviewer frame), each writing its criteria blind from the raw request, anchored by executable checks, position-swapped where pairwise. Their briefs, criteria, per-request results and scoring code are never visible to the optimiser; optimised agents see only "above margin / not" (the Ladder rule). **Independence is measured, not assumed:** inter-oracle exact and within-one agreement is recorded every loop; a rising agreement between oracles with no change in canary recall is treated as a warning of shared blind spots (Kim et al. 2025), not as corroboration.
- **Oracle protocol v1.1 (loop 1, DEC-77):** every rater is one model round over its prompt (the Codex rater runs without its user config, plugins or web search, with a no-tools rule; L-18); each rater writes criteria per request blind, before any artefact of that request exists, and keeps them across loops; the artefact sheet carries the frozen-test calls, coordinator probe calls at the edges of every stated range and on NaN, the assumption, the note and the question; the verdict follows from the rater's own Q1–Q3 (clean needs yes/yes/yes and no required change, any no is not-usable, otherwise usable-with-change), and the rater's stated verdict can only make it more severe (L-19). Any change to briefs, probes or rule replays the canary packet (three canaries, three known-clean fillers) before use.
- **Canaries:** the three loop-0 defect artefacts (wrong default on a safety-relevant charge limit; a capability that answered a question not asked; an unusable-output case) are replayed every loop against both oracles. **Canary recall must be 3/3 for the panel or the loop is void.** The canary set grows by one each time an oracle miss is later found by any means.
- **hc-01 result (Recorded, 17 Oct, n = 10; `campaigns/x1-spec-study/receipt/human-calibration/hc-01/RESULT.md`):** under the median and strict panel rules the three sealed raters (Sonnet technician, Opus reviewer, Codex GPT-6.1 technician) and the persona proxy agree on the same three of ten clean capabilities, while individually the raters called 4, 5 and 4 clean (corrected 18 Oct); three-level agreement is 6/10 within Claude and 4–5/10 across families; all caught the persona-rejected item. The panel therefore includes a cross-family oracle from loop 1 on, and the primary metric is the strict or median panel-clean rule.
- **Agentic calibration (loop-1 step 0, run hc-01):** the two oracles grade the ten blind loop-0 items; the receipts record oracle-vs-persona agreement, the persona proxy's false-accept rate as seen by each oracle, inter-oracle agreement, and canary recall. These are agent judgements of agent outputs and are labelled as such.
- **All review is agentic (DEC-78).** Persona reviews, oracle scoring, calibration, criteria audits and consumer use are performed by agent personas in sealed isolates, on more than one model family. No step uses, waits for or offers a human reviewer, audit or verdict. What a loop can claim is stated by the evidence it has: agent-corroborated clean promotion from the panel, agent-corroborated use from consumer agents exercising the capability through its runtime, and machine telemetry where a capability runs inside the app.

## What is fixed and what is climbable

Only three things are fixed, and they are fixed because without them no comparison means anything, not because they are in a document:

1. **The objective:** accepted useful capability per total cost, judged by a consumer who is blind to how the capability was made.
2. **The honesty rules** (listed under *Honesty rules* below): the optimised agents never read the judge; results are recorded as they fall; a difference is called a win only when it is readable above the measured noise.
3. **The record:** every departure from the spec is written down as a hypothesis with its test and its result, so a lost idea is not retried without new evidence and a won idea becomes the new spec.

Everything else is climbable, **the spec included**: Edition 3's architecture choices (the numeric WASM kernel as the only artifact class; declarative glue; the gate set G1–G7 and each gate's definition; the specification subsystem; the persona stage; the promotion statuses; the request-discovery trigger; the claim ladder's evidence sources), the request pool, the factory agents and their routing, and this method's own experimental design. Changing the ruler (oracle protocol, canaries, sealed set, scoring, guardrail thresholds) is slower only because changing the ruler and the thing measured in the same loop confounds the reading; a loop may still move the ruler if it runs the old and the new ruler side by side on the same artefacts.

## The deviation step (every loop)

Each loop, before the comparison runs, a fresh agent that is not running the loop's experiments reads the current spec (Edition 3, the errata, the factory protocol, this method) together with the previous loop's data and proposes **at least five materially distinct deviations from the spec**. Each proposal states: what the spec says; what the data says; the change; the predicted effect on the objective; the cost; how it would be tested in one loop. Proposals are ranked by expected gain per cost, and **at least one enters the loop as a tested arm or factor**. A deviation that wins is merged into the spec: version bump, an entry in `docs/coverage/EDITION-3-ERRATA.md` labelled with its evidence, and a decision record; the superseded text is kept with a `superseded by` note. A deviation that loses is recorded with its result. A deviation the loop could not afford is carried forward with its rank. "The spec says so" is not an argument against a proposal; "the spec says so and here is the measurement that supports it" is.

**Seed deviations for loop 1 (Proposed; from loop 0's data):**

- **D-01 Discover need from the app, not from a timer.** The protocol triggers on a timer and mines a corpus. The refrigeration-ai app is where technicians ask questions; questions the agent answered by reasoning alone, questions it could not answer, and capability calls whose follow-up question went unanswered are the real demand. Test: request sets from telemetry versus from corpus mining, compared on oracle-clean rate and consumer-agent usefulness (telemetry read-only, through the integration lead; until it exists, the 988-turn corpus stands in and the deviation is carried forward).
- **D-02 Fix, don't ship with a to-do list.** 15 of 18 shipped capabilities are `promoted-pending-change`: the spec records the persona's named change as metadata and ships. Better: the named change becomes a contract amendment and the kernel is regenerated once; only clean or with-assumption promotes. Test: fold the change into the 15 and re-run; measure clean rate and cost per clean.
- **D-03 Collapse the review stages.** Gates → persona stage → promotion is two reviews after the fact. The oracle panel's blind criteria can be written at contract time, before any kernel exists, and double as the acceptance test; the persona stage goes. Test: a factor in the screen (review block old/new).
- **D-04 Widen the artifact class.** A pure numeric kernel plus glue cannot serve an interface request, which is why the pool holds none. The evaluator stage inside the factory is part of the stack and moves on the fast loop; it is discovery feedback. Promotion authority lives in the oracle, the canaries and the person, which do not. This is the resolution of "everything moves" with "the judge is not in the optimisation step".

## Measurement

- **Unit:** configuration manifest (hash of every brief, prompt file, model id, effort flag, gate list, persona set, machine state) × request, paired by request, runs randomised and interleaved across time windows (never A then B in blocks).
- **Noise floor first:** an A/A replicate of the incumbent on the same requests with order and time randomised, every time the machine or model state changes (Kalibera–Jones dimensioning; Mytkowicz setup randomisation). Loop-0 arithmetic: two identical runs of 20 at a true 70 % differ by ≥20 points 23 % of the time; within-configuration CV of a model turn is 0.13–0.18; unpaired MDE on mean time at n = 20 per arm ≈ 26 s.
- **Reading a result:** time as log-scale paired differences with bootstrap CIs (Georges; Kalibera–Jones effect-size CIs); ordinal clean verdicts as paired sign tests on improved-vs-worsened requests; proportions reported with exact intervals and pooled across loops of the same configuration before being called changes; p95 logged as a guardrail observation, never adopted or rejected on at n = 20 (it is the 19th order statistic).
- **Subjects:** the 40 frozen reserve requests split into **20 working** (reused across loops under thresholded feedback) and **20 sealed** (scored every third loop, never tuned on); the 20 loop-0 requests are the open development set. The 988-question corpus is off-distribution (closed-form, no tool requests) and serves the guardrail and noise track only. Interface/tool requests do not exist in the pool; a person must author them before any X1-successor loop. Retrieval-by-fingerprint excludes working and sealed fingerprints (a cache hit on a test request is contamination, not compounding).
- **Forecast ledger:** before each loop, each move's predicted direction and size with a probability, plus **one named cross-stage interaction hypothesis**; Brier-scored after the run on questions phrased against the noise floor ("P(paired median wall difference exceeds the A/A floor)"), never on raw point estimates.

## Making interactions visible

A whole-stack contrast (all-new vs all-old) is one contrast; every stage effect is aliased with every other. Interactions become visible only by design:

1. **Preferred, when the token budget allows:** a 2^(4−1) resolution-IV screen over four stage blocks (specification/tests; generation; gates; review), old/new each: 8 variants × the 20 working requests = 160 runs. The all-new vs all-old corner is the owner's whole-stack contrast; the other six corners give stage main effects at 80-vs-80 (±11–14 points) and three aliased interaction pairs, flagged above 15 points. Any winning corner other than all-new becomes next loop's pre-registered hypothesis, never adopted on sight (winner's curse).
2. **Fallback, when it does not:** the four-corner design: all-old, all-new, and the two corners that test the one pre-registered interaction hypothesis.
3. **Always:** full configuration vectors and per-stage timings logged per run (per-stage wall is decomposable even when clean rate is not), accumulating toward functional ANOVA over many loops; an ablation path from old to new after an adopted win when a move is worth learning from.

The budget decision is made from measured tokens per request in the A/A phase, not from estimates: loop 0's single agent cost ≈75–83k tokens per request; with composition and single-shot workers (next section) the full screen is expected at 6–8M tokens per loop.

## Hill-climbing the hill-climb: the cost of a readable loop

The measurement has its own budget and its own hill. **Tokens per readable adoption decision at fixed power** is a tracked metric with a row in the stage budget, a forecast in the ledger and a move backlog of its own. The first estimate of a full screen (8 variants × 20 requests × 4–5 multi-turn agents × ~80k tokens ≈ 64M) is mostly structure, not measurement:

| Move on the measurement itself | Mechanism | Expected effect (Estimated) |
|---|---|---|
| **Composition, not repetition** | The stages are blind and independent given the stub, so a 2^(4−1) screen needs each stage generated once per (request, level): 4 × 2 × 20 = 160 stage-runs, and the 8 corners are assembled from those outputs; only gates and rendering run per corner | ≈4× fewer generation runs. Caveat: corners share components, so corner contrasts are not independent replicates; pair by request and by shared component, and never read the precision as if 160 independent runs were made |
| **Single-shot workers** | Everything in one prompt (request, protocol, templates, stub), all files in one response; the coordinator script runs the gates; the agent loops only on failure (2 in 20 in loop 0); invariant text first and the request last so the prefix cache can hit | ≈4–5× fewer tokens per stage-run (≈10–15k instead of ≈80k, which was mostly context re-read across 6–8 tool turns) |
| **Routing by stage** | **Sonnet 5.5 by default for every stage** (P-04b arm S3: 65.6 s per turn, 11/12 type-gate passes, and cheaper in the subscription's accounting), low effort for stub, glue and evaluator drafting; **Opus 5.5 only as the escalation** when a kernel fails its first gate pass; clean rate measured per stage per model. Side benefit: generators on one model and the oracle and persona panel on the other gives model diversity inside one provider (not full independence; errors correlate across providers too) | Fewer thinking tokens at equal visible output; several times more runs per subscription window |
| **Judge cost amortised** | Oracle criteria written once per request and reused across corners and loops; executable checks as scripts; persona panels only on corners that pass gates, two position-swapped calls each | Judge cost scales with requests, not with corners |
| **Fewer runs by design** | Request-complete blocks with pre-registered futility and success stops (minimum 12 requests); the incumbent corner is free from loop 2 (it was the previous challenger); balanced incomplete block allocation if still too much | ≈30 % fewer runs without cutting n per contrast |

Estimated loop cost after these moves: generation ≈2.4M, personas ≈2–3M, oracle ≈1M, A/A and canaries ≈1–2M, about **6–8M tokens per loop**, which fits a day's subscription windows and makes the full screen the default rather than the fallback. The A/A phase measures the real figure; the design decision in the charter uses the measured number.

**Precondition added:** per-stage token metering (input, cache-read, output, thinking per stage-run), recorded in the configuration vector, because today only per-agent totals exist.

## Rules that do not change between loops

Freeze the evaluator *procedure* per request before any candidate is evaluated (DEC-72); the person's confirmation is a question, not a sentence; probe and pilot numbers narrow and never decide (DEC-64); request text stays in `work/`; every brief and prompt is a versioned file hashed into the loop precommit, and model ids and machine state are hashed with them; consequence tier is assigned at the stub and physical-consequence requests stay at the Confirmed tier (E3 §7) whatever the loop says; each lesson must become a mechanism (invariant, gate, prompt line, retrieval entry) with a receipt or it is not learned.

**Honesty rules (the fixed part; hold whatever the result):** adopt on gate pass, wall time, persona acceptance or any score the optimised agents can read; let optimiser agents read oracle criteria, the sealed set or the canaries, or weaken a gate or guardrail to make a loop win; claim more than the machine evidence shows (agent-corroborated is labelled as such); standardise a configuration before the win has replicated on fresh requests.

## Departures from the spec and from the owner's directives

- Departures are the point: the spec is the incumbent and every loop must try to beat it (deviation step above). A departure is recorded as a hypothesis with its test; a departure without a record is drift.
- There is no human step and no human review of any kind; the owner directed this (DEC-74, DEC-78). Every persona is an agent.

- The oracle, canaries, sealed set and guardrail thresholds do not move on the fast loop. Reason: no non-trivial proxy is unhackable (Skalse et al. 2022) and repeated scoring overfits (Blum & Hardt 2015); the judge cannot be in the step it judges.
- The generator's self-check (compiling its own kernel before hand-over) is not a breach of blind separation: it never sees the tests. Declared because it could be read that way.
- The full screen is preferred but conditional on budget; the fallback tests one interaction per loop rather than all.

## Loop 1 charter (registered 2026-10-17: the owner approved it in the evening; amended to v2.1 under DEC-74 before any loop-1 observation was read; precommit hash in the capsule amendment and in `campaigns/x1-spec-study/receipt/notes.md`)

**Standing:** this charter is the current plan, not a law. The loop-1 session may change the design when it has a better idea, provided it writes the departure down as a hypothesis with its reason before running it and hashes the precommit for what it actually runs.

**Hypothesis (prospective):** moving the whole stack (parallel stub → evaluator ∥ generator ∥ contract-persona; properties and injected invariants; generator self-check and output caps; Sonnet-default routing with Opus escalation; width 2; retrieval excluding test fingerprints; contract-stage personas) raises clean promotion on the working set against the incumbent **v2 + low effort**, with guardrails intact. The incumbent includes low effort because it is the one move already measured (56.4 vs 90.6 s, same visible code); a bundle that cannot beat the obvious cheap move has earned nothing.

**Order:** (0) version and hash every brief; freeze the manifest; the two oracles grade the ten blind loop-0 items (hc-01). (1) Deviation step: a fresh agent proposes at least five deviations from the spec (seeds D-01 to D-07 above plus its own); the top-ranked affordable one enters the design as a tested arm or factor, and its precommit is written before step 3. (2) Both oracles write criteria for the 20 working requests blind; a fresh agent audits five criteria sheets for executable anchoring; canary dry-run on the loop-0 artefacts: 3/3 for the panel or stop. (3) Noise floor: v2 twice and v2+low-effort once on the 20 development requests, interleaved and randomised (60 runs); prediction: |Δclean| between the identical runs ≤ 15 points (P ≈ 0.77); if > 30, stop and resize; measure tokens per request. (4) Budget decision: full 8-corner screen by composition (160 stage-runs, corners assembled) if the measured token cost fits the subscription windows within two days, else the four-corner design, else the sequential design of D-07 if its simulation holds. (5) Runs in request-complete blocks so an early stop stays balanced; minimum 12 requests to analyse. (6) Both oracles score blind; five all-new promotions are exercised end-to-end by a consumer agent in the technician frame on fresh inputs (agent-corroborated use). (7) Effect-size CIs; no best-of-N; forecasts scored; deviations merged or recorded as lost.

**Acceptance (adoption of all-new):** paired clean gain ≥ +6 of 20 (30 points, above the 23 % phantom rate); all guardrails hold; canaries 3/3; inter-oracle within-one agreement ≥ 8/10 on the working set. **Failure meaning:** below +6 is "no evidence at this n", not "worse"; a guardrail breach is a rejection of the bundle, not of its parts; canary miss voids the loop. **Rollback:** the incumbent is never modified; the challenger is a separate manifest. **Response:** adopt → the challenger becomes the incumbent and the ablation path runs on the top two moves; no evidence → the four main effects and the interaction pair become next loop's hypotheses; two consecutive loops without a main effect ≥ 20 points → budget moves from variants to harvesting real requests and oracle work.

**Initial forecasts (to be Brier-scored):** P(inter-oracle exact agreement on hc-01 ≥ 6/10) = 0.5; P(both oracles catch the persona-rejected item) = 0.7; baseline clean on the development set ≈ 15 % [3, 38]; P(all-new ≥ +30 points) = 0.35; main-effect order specification/tests > review > generation ≈ gates ≈ 0 (generation and gates already near saturation); P(some interaction pair > 15 points) = 0.5; P(low effort alone reaches −30 % paired wall on multi-agent requests) = 0.6; P(Sonnet-default clean rate within 10 points of Opus-default on the working set) = 0.6.

**What loop 1 can conclude:** the noise floor; oracle validity against canaries and inter-oracle agreement; whether the whole stack moves clean promotion by ≥ 30 points on closed-form real requests; which stage blocks carry it (if the screen runs). **What it cannot:** anything about interface/tool requests; durability (needs replication on the sealed set); which member of an aliased pair is real; that a person found a capability useful, until production telemetry (D-05) or an audit supplies it.
