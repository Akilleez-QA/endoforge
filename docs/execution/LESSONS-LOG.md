# Lessons log

Dated, operational lessons that would otherwise live only in a conversation. Each entry says what happened, what it changes, and where the evidence is. Design decisions go to R16; risks to R15; this log is for the things learned while doing the work. Labels follow `docs/CONVENTIONS.md`.

## 2026-10-17

### L-01 The model turn is thinking-dominated, not context-dominated
- **What happened.** P-04 measured `claude -p` turns at ~94 s wall with ~453k–468k cache-read tokens of CLI context (MCP tool schemas) and assumed the context explained the time. P-04b's lean arm stripped the context to ~7.2k tokens and the turn still took 77–118 s with 8.7k–13.2k output tokens, half of them thinking (Recorded (probe), `experiments/P-04b-bare-api-model-term/receipt/raw/S1-lean-A-*.json`).
- **What it changes.** The lever on latency is thinking budget and output length (`--effort`, prompt wording that forbids prose), not context size. C05's arms and WP24a's design should vary effort and output constraints before anything else. Edition 3 §10's "≈1,000 tokens, 5–10 s" is off by about 10× in this configuration (E3-20).
- **Also seen.** Through the CLI, a variant prompt that shares a 2.6k-token prefix did not read that prefix from cache (only the system prompt was cached): prompt-cache behaviour through the CLI is not the API's, so cache claims need the API or a controlled runner.

### L-02 CLI authentication is per-account and does not pass to child processes
- **What happened.** The desktop app's session was logged in, but a child `claude -p` reported `loggedIn: false` with a stale 3 Oct token; `claude login` in a terminal opened an interactive session instead of logging in (it treated "login" as a prompt). The user then logged the CLI into a different account than the desktop app.
- **What it changes.** Any probe that runs `claude -p` must assert its own login state (`claude auth status`) and that `ANTHROPIC_API_KEY` is unset (in `-p` mode a key is always used when present and switches billing to the API). P-04b's runner does both. Usage from such probes draws on the CLI account's subscription limits, not the desktop's.

### L-03 The user chose subscription-only model measurement
- **What happened.** P-04b was briefed to use the Messages API; no key existed and the user decided not to use the API at all ("use our sub"). The docs confirm scripted `claude -p` under a personal subscription of the unmodified binary is supported for individual use; `--bare` and `--betas` are key-gated; all `-p` runs count against the 5-hour and weekly limits (`docs/reference/R18` SRC entries for the CLI docs; checked 2026-10-17).
- **What it changes.** C05 (X5) has no bare-API arm until that decision changes; the hosted baseline is the lean CLI arm. R14 and C05 must say so.

### L-04 A frozen evaluator must be total over arbitrary candidate output
- **What happened.** P-03's evaluator v1 crashed inside the invariant layer on mutant output (an empty effects list; a row citing a non-existent reading) before any outcome was recorded, and had to be revised once (both hashes kept, `experiments/P-03-escape-rate-method/receipt/evaluator-revision-1.md`).
- **What it changes.** WP09's acceptance criteria: every gate and invariant is exception-safe and returns a verdict for any input shape; a crash is a reject with a named reason, never an absence of a verdict. The fault generator (WP11) needs a rule for spec-ambiguous non-faults (3 of P-03's 12 base escapees), and a "compose top scorers" searched stratum degenerates when the top scorers are the escapees themselves (C03 must define S4 differently).

### L-05 The invariant layer carries the discriminating power
- **What happened.** On P-03's toy, universal gates alone left 68.8 % of mutants escaping; adding domain invariants cut that to 35.4 %; for domain-semantic faults the gates killed 0/23 and the invariants 19/23 (Recorded (probe)).
- **What it changes.** It is probe-level support for Edition 3 §6's bet that the invariant library is the compounding asset, and for ordering the plan evaluation-plane first. It does not establish any real escape rate.

### L-06 Disagreement inputs separate most, not all, survivors
- **What happened.** On P-03, one answered disagreement input frozen as a test killed 58 of 68 escapees; the remaining 10 needed inputs of a different shape (prior state, float boundaries, ordering) that random drawing reaches slowly or never.
- **What it changes.** R19 §2.1 keeps its Stage 6+ item, with a note that the input generator must be shape-aware, not uniform random.

### L-07 Probe processes die with the parent session
- **What happened.** The desktop session crashed mid-afternoon; a background runner for P-04b and a mining agent were killed with it. One runner survived long enough to finish a turn; the receipts were intact, and both were resumed from their transcripts/receipts without loss.
- **What it changes.** Long runners should write every sample to disk as it completes (they did), be idempotent on resume (P-04b's was), and record provenance when two runners' samples are adjacent (noted in its RESULT.md). Consider `systemd-run --user` for anything over 30 minutes so it outlives the session.

### L-08 Cross-session messages are held across permission modes
- **What happened.** Messages to the refrigeration-ai session were held because it runs in a different permission mode, and expired unapproved. The information arrived anyway because that session wrote its list to a shared, git-ignored folder in this repository.
- **What it changes.** Hand-offs between sessions go through files in the repository (under `work/` when private), not through session messages; the message, if any, only names the file.

### L-09 The X1 pool's provenance
- **What happened.** The 60-request pool was assembled from: 8 verbatim technician questions chosen by the refrigeration-ai session from a 199-turn stratified sample; 4 owner process requests and 5 recorded owner decisions; 1 owner GitHub issue; 4 items from the owner's own earlier plant work (private study, names replaced); 2 derived from the corpus; and 36 verbatim, redacted calculation requests selected by keyword scoring from all 1,001 substantive turns in the 550 public chatbot transcripts (Mar–Apr 2025). The owner vouched for rule 1 in chat; LOW-confidence candidates (persona reviews, engineering inferences) were excluded. The mining agent's "shape guess" notes were stripped from the pool files so the specifier is not primed.
- **What it changes.** C01 §6's workload row can be filled: pool digest `receipt/pool.sha256`, freeze `receipt/freeze.sha256` = `df0684d6…`, seed 20261017, primary 20, reserve 40. The reserve is almost entirely chatbot calculations, so if the extension to 60 fires, the extended set's composition differs from the primary's; the analysis must report the primary and extended sets separately (it does).

### L-11 The dark-factory run: 20 real requests, 19 gated capabilities, nothing a person could not have asked for
- **What happened.** The owner redirected X1 from a human specifier to the factory loop ("discover need, create code, promote candidate to user"; "the whole point is to use agents"). One fresh agent per primary request wrote a contract and executable tests, froze them by hash, generated an AssemblyScript kernel, and ran fixed gates (`campaigns/x1-spec-study/factory/gate.mjs`); `promote.mjs` re-ran every gate independently. **19/20 promoted with a stated assumption, 1 self-rejected, 20/20 under 600 s (median 95 s, p95 147 s), 18/20 passed the gates on the first run** (Recorded (probe); `receipt/factory-summary.json`, `receipt/summary.json`). Promoted kernels run: dew point 60 °F/60 % → 46.1 °F; −10 °F/50 % → −22.3 °F (over ice); 6.2 kW → 8.31 hp; R-448A at 100 °F → 241 psig; the owner's plant reaction code; the qualification-floor gate.
- **What it does not show.** No person used any capability, so claim-ladder rung 4 is unchanged. C01 was never formally registered (no named author/reviewer, no campaign id), so this is a pilot of C01 under an agent specifier, not a C01 result. Completeness is the workers' self-report; the blind rater agreed 10/10 on `complete` (κ = 1 is uninformative with no variance), 9/10 on `underdetermined`, 8/10 on `composable`, 5/10 on shape, and counted residual assertions higher on 7 of 10 items (it counted assumption-pin and boundary rows; rater 1 did not): the rubric's residual-counting rule needs tightening before X2.
- **What it changes.** (1) The specification cost that Edition 3 §3 worried about is not where the difficulty is for an agent specifier: contracts took 1–2.5 minutes. (2) **Every one of the 20 requests was underdetermined** (20/20 rater 1, 9/10 rater 2): the technician never names the fact that fixes the answer. The factory's natural product is therefore "a capability plus the one question", and promotion-with-assumption is the normal outcome, not the exception; Edition 4 should make the question a first-class output and R19 §2.1's disagreement loop the way it gets answered. (3) The one rejection was an evaluator-format defect (JSON cannot carry NaN), the same class as P-03's lesson L-04: evaluator totality now includes the test format. (4) Two of 20 needed one compile repair each (AssemblyScript diagnostics), consistent with P-04's 13/13 type-gate passes: the type gate is not the bottleneck. (5) Shape clusters: 15 in 20 by the coordinator, 4 families by the blind rater reading contracts alone — clustering is rater-dependent and needs a defined procedure before it can inform R19 §2.5.

### L-12 Process notes from running 20 agents at once
- The kit's `start` hint pointed at `work/contracts/<id>.md` while the factory protocol used `work/factory/<id>/CONTRACT.md`; every worker noticed and followed the protocol, three also wrote a copy to the hinted path. Fix the hint (or make the factory path the kit's path) before the next run.

- Concurrent agents spent roughly 75–83k tokens each (about 1.6M tokens for the run) and finished in 1.5–3.5 minutes wall each; the machine was under load from P-04b at the same time, so the working seconds are an upper bound.

### L-13 Persona checks on the 19 promoted capabilities
- **What happened.** An agent applied the house persona-review method (ten named personas; 2–3 per capability by who would ask) to the 19 promoted kernels, running each on its usage example plus persona-realistic and edge inputs (155 calls, 25 expected traps, 1 value outside its stated fit range). **43 verdicts: 14 accept, 27 accept-with-change, 2 reject.** Only 3 capabilities (CC-014, CC-025, CC-036) were accepted by every persona. The rejections: C-006 chose the wrong default equipment class for an A3 (R-290) charge limit, an unsafe default for the question asked; CC-011 answered a question that was not asked (a cost formula for a price question). Receipt: `campaigns/x1-spec-study/receipt/persona-review-summary.md`; full report and a 21-item proposed backlog under `work/persona-review/`.
- **What it changes.** The gates certify that a kernel does what its contract says; they say nothing about whether the contract is the capability the person wanted. Persona review is the cheapest proxy for the confirmation step Edition 3 §6 puts on the person, and it finds a different class of defect from the gates: wrong default (C-006), wrong question (CC-011), unusable presentation (the five cross-cutting items: trap codes need a message, print the assumption with every answer, field precision and units, label every code, one kernel per quantity). "Promoted" should therefore mean gated **and** persona-accepted; the plan's promotion rule (WP28/C14) and R04's legibility section need the persona verdict as a stage, and the factory protocol needs the five presentation rules as universal gates on the glue, not on the kernel.

### L-14 Promotion means gated and persona-accepted; the presentation rules fit on the glue
- **What happened.** The factory protocol was extended as L-13 asked: a declarative `glue.json` per capability (exports, argument names and units, integer-code and boolean labels, result unit and field precision, the assumption, the question, a message per trap), a closed schema, and gate **G7** that fails when any of those is missing; `promote.mjs` now promotes only a gated capability whose `persona.json` carries no reject, and lists accept-with-change separately as promoted-pending-change. The 17 unrejected capabilities received glue from their contracts with no kernel change (17/17 G1 hashes and wasm digests intact). C-006 and CC-011 were voided and rebuilt by fresh workers with the persona findings as input (132 s and 74 s), then reviewed by a fresh blind persona agent. **Result: of 20 requests, 19 gated; 3 promoted (every persona accepts), 15 promoted pending one named change, 1 gated but persona-rejected (CC-011), 1 gate-rejected (CC-001)** (Recorded (probe), `campaigns/x1-spec-study/receipt/factory-summary.json`, `receipt/notes.md`).
- **What it does not show.** Persona acceptance is still a proxy: no person has used a capability (rung 4 unchanged). The 17 `persona.json` files are backfilled from one report by one agent, not fresh per-id reviews. The persona receipt's totals line overstated the count (41 verdicts, not 43); the corrected figures are in the receipt.
- **What it changes.** (1) The five presentation rules are enforceable as a gate on the glue without touching a frozen kernel: 17 backfills passed G7 with zero kernel edits, so legibility is a property of the glue, as R04 and WP26 assume. (2) A persona rejection is not always repairable by the factory: CC-011's second rejection says the request ("what does 15 lb cost") needs a bound price source, which no kernel holds; the honest outcome is gated-but-not-promoted with the question recorded, and the product's answer is a binding (WP26), not a kernel. C-006's rejection was repairable: the wrong default became the explicit alternative and the new default is the cap the persona expected. (3) "Promoted" shrank from 19 to 3 under the stricter rule; the 15 pending items each name one change, which is the backlog the next factory round should take as input, the way C-006's re-run did. (4) A worker given persona findings as part of the need, not as a consultation, kept inside the protocol (one round each); handing findings forward is the loop R19 §2.1 describes, and it cost one void per id.

### L-15 Fixed evaluators are enough only where the task was made deterministic
- **What happened.** The pilot's frozen example tests held because Edition 3's kernel contract makes the task deterministic by construction (pure function, numbers in and out); 19/19 gated kernels passed an independent re-run. The owner's point, 17 Oct evening: fixed evals are not good enough for non-deterministic tasks and code, such as a user asking for a tool that needs an interface. The day's own evidence agrees: in P-03 the invariant layer killed 19/23 semantic faults where the six example tests killed far fewer; disagreement inputs (a generator, not a list) killed 58/68 escapees; P-06's exhaustive check beat any example set; and the persona stage found what two agent raters agreed was complete.
- **What it changes.** The principle is **freeze the procedure, not the examples**: the committed, hashed evaluator is the generator (properties and metamorphic relations, input generators with seeds, differential and exhaustive checks where a reference exists, sample sizes and an acceptance rule with pre-registered power, judge framings), and each candidate faces a fresh draw from it. "Before and blind" and "frozen" (E3 §6) keep their meaning; "the test was wrong" stops being a temptation because the test is not a fixed list. For an interface request the delivered tool splits into four parts with different regimes: logic (pure kernel: fixed tests, properties, exhaustive checks), view specification (data under a closed schema: deterministic checks, source binding, permitted effects, the question shown), interaction behaviour (scenario tests through the real renderer, metamorphic relations, state preservation on revision; the lab's uihill pipeline), and fit to the person (independently framed judgement, then the person's answer to one question). Push as much as possible into the first two; price the last two into X1's successor rather than hiding them in examples. WP09 becomes properties-first; C02 and C03 register generators and power, not fixtures (DEC-72).

### L-16 Evaluator and code should be made in parallel, by different blind agents
- **What happened.** The pilot's per-request agent wrote the tests, froze them, then wrote the kernel: one reading of the request produced both. CC-001 shows the cost: a test and a kernel that agreed on a wrong representation. Edition 3 §10 already names overlapping evaluator synthesis with generation as a latency lever ("the evaluator's hash is frozen before evaluation, not before generation starts"); the owner's direction, 17 Oct evening, is to use it.
- **What it changes.** Factory v3 protocol (Proposed): (A) one short agent fixes the interface stub, the stated assumption and the one question, hashed; (B) concurrently and blind to each other, an evaluator agent writes the procedure (DEC-72), one or more generator agents write kernel and glue against the stub, and a contract-persona agent judges the assumption and question before any code exists; (C) the evaluator hash is frozen before evaluation, then gates, output personas, promotion. Expected effects: wall time max(spec, generate) instead of the sum (about 60 s against today's ~100 s, Estimated); a genuinely independent second error source under E3 §7; intent misses caught before a build. The frozen 40-request reserve allows a direct comparison of v3 against today's sequential 20 on time, first-pass yield, persona rejections and evaluator defects.

## 2026-10-18

### L-17 A single-shot metered worker reproduces factory v2 at a fifth of the tokens
- **What happened.** Loop 1's incumbent runs the loop-0 protocol (contract and tests, freeze, kernel and glue, up to three gate repairs, a blind persona stage) as one `claude -p` call per stage with the lean flags of P-04b, the coordinator running the gates. On the 20 development requests, twice: 40/40 gated on the first round, median 46 s per run, 18.2k tokens per run (worker 11.1k, persona 7.1k), against loop 0's 75-83k tokens and 97 s with a multi-turn Agent-tool worker (Recorded (probe); `campaigns/hillclimb-loop-01/receipt/noise-floor.json`, `tokens.jsonl`).
- **What it changes.** Most of loop 0's cost was the harness (tool turns re-reading context), not the protocol. Per-stage metering through the CLI's usage block is what made the loop's budget readable; the Agent tool reports only totals. The factory's cost model (E3 §10) should be stated per single-shot stage, not per agent.

### L-18 A cross-family oracle must be a single model round: strip its tools
- **What happened.** The Codex CLI oracle, given the same criteria brief as the Sonnet oracle, ran web searches (seven in one batch) and reached the MCP tools of the user's config, each a full-context model round: five criteria batches cost 1.3M metered tokens. Under protocol v1.1 (`--ignore-user-config`, `-m gpt-6.1-sol`, `web_search="disabled"`, a no-tools rule in the prompt) a five-request batch costs about 21k tokens in one round (Recorded (probe); `receipt/tokens.jsonl`, `receipt/oracle-protocol-revisions.jsonl`). The deviation critic, which legitimately reads files, cost 0.75M for 20 reads.
- **What it changes.** The oracle protocol fixes the tool surface of every rater, not only its prompt; a rater that can search has a different, non-reproducible evidence base from one that cannot. Meter every provider by the same rule (input, cached input, output) and watch per-call rounds, not only totals.

### L-19 Criteria written first change the verdict: the verdict must follow from "answers the question asked"
- **What happened.** The canary dry-run under the v1 scoring briefs caught CC-009 (3/3) and C-006 (2/3) but not CC-011 (1/3): all three oracles' own criteria for the price request say the calculator must ask for a quote, and the technician frames then graded the quote checker against that, one of them with Q1 "partly" and a stated verdict of clean. In hc-01, without criteria, every rater had called the same artefact not usable. The slow-loop revision (scoring briefs v2): the verdict follows from Q1-Q3 (clean needs yes/yes/yes and no required change; any no is not-usable), the stated verdict can only make it more severe, and the wrong-question class is stated as a rule (a capability that can only answer by being given the quantity asked for does not answer the question). Attempt 2 passed 3/3 with no filler false-rejected (Recorded (probe); `receipt/canary-dryrun.jsonl`).
- **What it changes.** The canary set did its job on the first loop: a ruler change (criteria) silently moved a verdict and the replay caught it before anything was scored. The method's definition of clean is now mechanical in the scorer; a future oracle change must replay the canaries before use, as the method says.

### L-20 A gate convention can steer the worker into satisfying the harness
- **What happened.** G7 requires `glue.id` to equal the artefact folder name. The kit's first run folders were named by arm and request, so round 1 failed G7 and the repair round obediently renamed the id to the folder name. Artefact folders are now named by request id (`<run>/<id>/`); the incumbent then gated in one round (Recorded (probe); `work/runs/smoke-1-prelayoutfix/`).
- **What it changes.** Gate feedback is an instruction channel: whatever the gate names, the worker will satisfy, including harness accidents. Layout rules that gates depend on belong in the freeze record, and a repair round that changes an identity field should be a validator error, not a repair.

### L-21 The noise floor at n = 20 under the median panel rule is one request; the strict rule is degenerate
- **What happened.** Two identical incumbent runs on the 20 development requests: clean 4 and 3 under the median rule (|delta| = 1 of 20, inside the precommitted bound of 3), per-request clean agreement 17/20, gated 20/20 and 20/20, promoted 17/17. Under the strict rule (all three oracles clean) both runs score 0/20: the Opus reviewer called 2 of 40 artefacts clean and the Codex technician 8 of 40 with almost no middle level (2 of 40 usable-with-change), so unanimity on clean almost never occurs. Within-one agreement 38-39/40 for every pair; on the clean/not-clean split, kappa 0.75 Sonnet-Codex, 0.13 Opus-Codex, -0.08 Sonnet-Opus (Recorded (probe); `receipt/noise-floor.json`, `scores-s3.jsonl`).
- **What it changes.** The median rule is the usable primary, as precommitted; the strict rate is reported but cannot move at this n. The incumbent's clean rate on the development set (15-20 %) matches the charter's forecast (15 % [3, 38]) and loop 0's persona-clean 3/19, so the sealed panel and the persona proxy agree on the base rate. The raters disagree in the middle, not on the split; the critic's structural-majority concern (two Claude raters) is visible in the kappas and stays recorded.

### L-23 The all-new bundle costs five times the incumbent and buys no clean promotion; its generation stage alone is cheaper than the incumbent
- **What happened.** The challenger's full path (stub, contract-stage persona, blind evaluator, two blind Sonnet candidates, output persona, one bounded repair) cost 94-99k tokens and 159-188 s per request against the incumbent's 19-21k and 51-52 s; both pre-registered guardrails (2.0x wall, 3.0x tokens) were breached, which rejects the bundle as a bundle. ### L-24 One bounded repair driven by a blind output review did not resolve the reviewers' findings
- **What happened.** D-02 triggered on 18 of 20 working and 15 of 20 sealed artefacts (the output personas named a change on almost everything); after the amended stub, the re-frozen spec and one new blind candidate, both personas accepted the repaired artefact on 4 of 18 and 0 of 15, and no repaired artefact became panel-clean. D-02 is recorded as lost at this n with its price; a repair that targets the oracle-visible surface (refusal text naming the input, impossible results refused, assumption text that follows the inputs) is the version worth pricing, because those are what the panel and the consumer agents named most.

### L-25 Agent-corroborated use repeats the panel: right numbers, wrong shape
- **What happened.** Five challenger promotions were used end to end by fresh Sonnet technician agents through `try.mjs` (23 recorded calls): one answered the question outright, three partly, one not at all (a capability that only refuses); two would be used on the job; every stated assumption was accepted. The technicians' changes: refusals that do not name the input at fault, impossible results returned silently (a negative superheat, a negative non-condensable pressure, a saturation temperature past the critical point), assumption text that does not follow the inputs typed, a P-T fit 2-9 F off a published chart (Recorded (probe); `receipt/consumer-use.json`; the reports are the agents' own words).
- **What it changes.** The defect classes are presentation-and-contract classes that a gate can see once named (a refusal must name the argument at fault, which the glue's one-trap-many-conditions shape cannot express; a result outside physical bounds must refuse). These are gate additions for loop 2's deviation list, not kernel changes. The claim ceiling is unchanged: agent-corroborated use, no person.
